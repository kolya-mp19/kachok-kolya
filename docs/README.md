# Документация проекта

Бизнес-документация приложения для планирования и отслеживания силовых тренировок.
Отвечает на вопросы **что** и **почему**. На вопрос **как** отвечают PRD, которые
составляются на её основе отдельным этапом.

## Порядок чтения

Новому участнику — сверху вниз:

1. **[Принципы продукта](./principles.md)** — методическая позиция (П1–П4). Продукт не нейтрален,
   и это осознанно. Без этого файла остальные документы выглядят набором произвольных решений.
2. **[Карта контекстов](../CONTEXT-MAP.md)** — две независимые предметные области и почему между
   ними нет связей.
3. **Глоссарии** — [дневник](./domain/training-log/CONTEXT.md),
   [калькулятор](./domain/calculator/CONTEXT.md). Канонические термины и запрещённые синонимы.
4. **[Спеки фич](./requirements/README.md)** — что делаем и почему.
5. **[ADR](./architecture/adr/README.md)** — принятые решения и отвергнутые альтернативы.

## Что где лежит

| Каталог | Содержимое | Когда сюда пишут |
|---|---|---|
| `principles.md` | Методическая позиция продукта | Когда продукт занимает позицию, влияющую на несколько фич |
| `domain/<контекст>/CONTEXT.md` | Глоссарий. Только термины | Как только термин устоялся. Правил и реализации здесь нет |
| `requirements/<фича>/index.md` | Бизнес-спека фичи | При проработке фичи. Каркас — в `requirements/_templates/` |
| `architecture/adr/ADR-NNNN-*.md` | Решение и отвергнутые альтернативы | Когда решение трудно обратить, оно неочевидно и был реальный выбор |

Внутри папки фичи по мере надобности заводятся `data-model.md`, `screens.md`,
`open-questions.md` — но `index.md` остаётся главным входом.

## Правила

- Всё на **русском языке**. Имена файлов — латиницей, kebab-case.
- Термин из глоссария употребляется **только** в каноническом виде. Синонимы из списка
  `_Избегать_` не используются нигде, включая интерфейс.
- Правило попадает в спеку, если пользователь способен его заметить и с ним не согласиться.
  Механика вроде разрядности округления или порядка обновления состояния — не попадает.
- Раздел «Границы фичи» стоит раньше потока и правил намеренно: тот, кто читает документ, чтобы
  проектировать по нему, должен сначала узнать, чего делать **не** надо.
