# Окружения и внешние доступы

Проектный результат [E003-T002](../tasks/t002-environments-and-access.md) для
[E004](../../e004-project-foundation/prd.md), [E006](../../e006-delivery-foundation/prd.md)
и интеграций [E009](../../e009-email-access/prd.md)–[E010](../../e010-provider-access/prd.md).
Опирается на принятые [стек](../../e001-technical-design/design/technology-stack.md)
и [границы доверия](../../e001-technical-design/design/access-and-trust.md).
Здесь определяются условия подключения; аккаунты, домены и инфраструктура не создаются.

## Границы решения

Один рабочий сервер с Docker Compose обслуживает HTTPS, статику React SPA, NestJS
и внутреннюю PostgreSQL. БД не публикуется в интернете. SPA и API каждого окружения
используют один origin; калькулятор остаётся отдельной клиентской точкой без API.
Тестовый Compose-проект допускается на том же сервере при независимых ресурсах
и ограничении нагрузки: отдельный сервер не становится обязательным расходом.
Это разделение конфигурации и данных, а не защита от компрометации общего хоста.

Аудитория — владелец и ещё несколько человек, ожидаемая нагрузка минимальна;
используется имеющийся сервер. Бюджет исключён из рассмотрения прямым указанием
владельца и не является блокером проектирования. Условия передаются из
[E003-T001](../tasks/t001-audience-and-constraints.md). Наличие управляемого домена,
почтового сервиса и внешних кабинетов из этого не следует: их фактическое подключение
ещё не проверено. Подготовка проекта не означает заказ новых услуг.

## Три окружения

| Окружение | Назначение и доступ | Данные и хранение | Почта и провайдеры |
|---|---|---|---|
| Локальное | Машина разработчика, сервисы привязаны к loopback; мобильный доступ только по явно настроенному защищённому адресу | Синтетические атлеты, отдельная PostgreSQL и том; чистый запуск не требует рабочего дампа | Локальный приёмник писем без исходящей доставки; имитации ответов OAuth для обычных тестов, реальные тестовые учётные записи только для интеграционной проверки |
| Тестовое | Отдельный HTTPS-origin; закрыт от случайного внешнего доступа на reverse proxy, разрешён владельцу и проверяющим | Синтетические дневники; собственные Compose project name, сеть, том БД, роль и пароль; рабочие данные не копируются | Отдельные OAuth-приложения и тестовые аккаунты; письма перехватываются внутренним приёмником без внешнего SMTP |
| Рабочее | Постоянный HTTPS-origin для согласованной аудитории | Личные дневники; отдельные том, сеть, роль и пароль; очистка тестового проекта не затрагивает рабочее хранилище | Рабочие OAuth-приложения и доставка подтверждений/восстановления через согласованного почтового поставщика |

На общем сервере PostgreSQL запускается отдельным контейнером для каждого окружения,
а не несколькими схемами одной БД. Сетевые имена и монтирования разрешаются только
внутри своего Compose-проекта. Имена томов не должны совпадать через общий внешний том.
Резервный объём и пределы тестовых контейнеров определяются после проверки ёмкости
сервера: если тест способен вытеснить рабочую БД по памяти или диску, одновременный
запуск запрещён до изменения размещения. Ограничения и остаток ресурсов проверяет
оператор в E006; предположение о достаточной ёмкости не является результатом проверки.

Cookie дневника привязывается к своему хосту без общего Domain для поддоменов.
Origin, адрес ссылок писем и redirect URI задаются доверенной конфигурацией окружения;
не строятся из входящего Host. Рабочая cookie не должна попадать в тестовый origin.
Локальное защищённое соединение нужно отдельно проверить для Secure-cookie и
мобильного телефона; обычный HTTP на локальной машине не доказывает эти сценарии.

## Ответственные и получение доступов

| Роль | Ответственность | Кто выполняет в первой версии |
|---|---|---|
| Владелец продукта | Определяет аудиторию и решение о выпуске; владеет контактами восстановления внешних кабинетов | Владелец репозитория; бюджет по его указанию не рассматривается |
| Оператор | Настраивает сервер, DNS/TLS, почту, кабинеты OAuth и закрытое хранение секретов; выпускает версию по инструкции | Владелец, подтвердивший сопровождение Compose/Node.js/PostgreSQL в [E001](../../e001-technical-design/design/constraints.md); делегирование требует отдельного доступа, а не передачи главного пароля |
| Разработчик | Готовит код и описание параметров, использует локальные/тестовые доступы; не получает рабочие секреты для обычной проверки | Исполнитель соответствующего эпика |
| Проверяющий | Проверяет синтетические дневники и фиксирует результат; не меняет рабочую конфигурацию | Назначается владельцем перед прогоном E006/E028 |

Оператор получает доступ к серверу по личному SSH-ключу; доступ к DNS, почте и OAuth
остаётся в кабинете владельца с доступным ему восстановлением. Если сервис допускает
приглашение оператора, выдаются необходимые полномочия отдельно. При смене оператора
его доступ отзывается, общие секреты, которыми он владел, заменяются. Конкретный сервис
хранения паролей не навязывается; владелец обеспечивает закрытое хранилище вне git.

Для работы с телефона и OAuth нужен постоянный DNS-адрес и доверенный TLS-сертификат.
Покупка нового домена необязательна, если у владельца есть управляемый домен/поддомен.
Рабочее и тестовое окружения получают разные хосты; точные адреса фиксируются после
подтверждения DNS. Пример домена в документации не становится адресом регистрации.
Смена рабочего origin требует отдельной проверки cookie, ссылок писем, OAuth callback
и локальных черновиков: хранилище прежнего origin автоматически не переносится.

## Проверенная основа и незавершённые внешние входы

Проверка официальной документации подтверждает техническую схему, но не наличие
прав, доступность кабинета владельцу, оплату или фактическую доставку с его сервера.

| Зависимость | Что подтверждено источником | Что оператор должен получить и проверить до подключения |
|---|---|---|
| Размещение | Compose позволяет дать секрет конкретному сервису через файл; [документация Docker](https://docs.docker.com/compose/how-tos/use-secrets/) | Доступ к имеющемуся Linux-хосту с Docker/Compose, диску и DNS; возможность входящего HTTPS и исходящих обращений к почте/OAuth; достаточная ёмкость |
| Яндекс ID | [Регистрация приложения](https://yandex.ru/dev/id/doc/ru/register-auth) предусматривает платформу веб-сервиса, redirect URI, контактную почту и разрешения | Кабинет владельца с восстановлением, отдельные тестовое и рабочее приложения, права на имя/почту и точные callback; доступность нужных разрешений и требования верификации для фактического сервиса |
| VK ID | [Официальный SDK](https://github.com/VKCOM/vkid-web-sdk) требует APP_ID из кабинета и задаёт redirectUrl, state и codeVerifier | Создание приложений Web, разрешение на почту, домены/callback, тестовые аккаунты и применимые требования кабинета; портал документации не открылся при исследовании, поэтому порядок регистрации и доступность проекта ещё не подтверждены |
| Рабочая почта | Требования приложения заданы [потоком E001](../../e001-technical-design/design/access-and-trust.md): подтверждение адреса и восстановление после транзакции | Получить у владельца доступный сервис отправки; проверить разрешённую транзакционную отправку, лимиты, DNS-подтверждение отправителя, TLS и доступ из сети сервера; затем реальную доставку на контролируемые адреса в E009 |
| Домен и TLS | Постоянный origin необходим выбранной схеме cookie и callback | Подтвердить управление DNS, выпуск/продление доверенного сертификата и отсутствие конфликтов адресов; поставщик не выбран |

В E010 сверяется актуальный протокол VK ID по кабинету и официальной спецификации,
включая code/PKCE и device_id. Тестовые имитации не подменяют реальный проход обоих
провайдеров; отсутствие подтверждённого доступа не исправляется молчаливым исключением
способа входа из первой версии. При невозможности подключения решение возвращается
в условия выпуска до реализации интеграции.

## Конфигурация и секреты

| Группа | Что допустимо в git | Что хранится только вне git |
|---|---|---|
| Окружение | Назначение параметров: идентификатор окружения, origin, timezone Europe/Moscow, ссылки на инструкции | Фактические доступы хоста и кабинетов |
| PostgreSQL | Имена назначений и путь чтения секрета; правила миграций | Пароли ролей и строка подключения с паролем |
| OAuth | Перечень провайдеров, назначение client/app ID и точных callback; значения ID не являются доказательством доступа | Client secret и прочие закрытые ключи конкретного приложения; code/verifier/token не журналируются |
| Почта | Назначение адреса отправителя и режима доставки; для local/test обязательный перехват | Рабочие SMTP/API credentials и доступ восстановления почтового кабинета |
| Приложение | Назначение ключей и формат конфигурации | Все закрытые ключи, требуемые протоколом сессий и [черновиков E001](../../e001-technical-design/design/input-preservation.md) |

1. Разработчик описывает имена, назначение, обязательность и способ чтения параметров
   без значений. E004/E006 создают шаблоны только при отдельном начале реализации S02.
2. Оператор генерирует независимые значения для каждого окружения и сохраняет их
   в закрытом хранилище владельца. Передача выполняется по защищённому каналу,
   без чата задачи, issue, коммита или истории shell.
3. На хосте секреты размещаются в каталоге вне checkout с правами только оператора
   и необходимых процессов. Compose монтирует конкретные файлы только нужным сервисам.
   Приложение явно читает файлы; суффикс `_FILE` не считается автоматически
   поддержанным NestJS или Prisma. Строка БД собирается сервером без вывода в журнал.
4. Сборка SPA получает только публичную конфигурацию. Секреты не передаются через
   переменные Vite, аргументы сборки, Dockerfile или слои образа. Обычная автоматическая
   проверка не получает полномочия выпуска; этап развёртывания получает только своё окружение.
5. Оператор проверяет доступность параметров без печати значений. При замене секрета
   сначала проверяет новую конфигурацию, затем отзывает старую; влияние на активные
   сессии и черновики проверяется по протоколу E001. Замена ключа не должна молча
   уничтожать доступ к сохранённым черновикам.

Compose secrets на обычном хосте монтируются из файлов и сами по себе не шифруют
исходные файлы на диске. Защита и сохранность каталога остаются обязанностью оператора.
Архивы конфигурации с секретами также не попадают в git или артефакты сборки.

## Защита тестовой почты и данных

В local/test приложение не получает рабочие SMTP/API credentials. Весь поток писем
направляется во внутренний приёмник, который не пересылает сообщения наружу;
сеть приложения не разрешает обход приёмника через внешний почтовый API/SMTP.
Адрес получателя из тела запроса не меняет маршрут доставки. Проверяются в том числе
восстановление и подтверждение при подставленном настоящем адресе: письмо видно
только в закрытом тестовом приёмнике. Его интерфейс недоступен атлетам рабочего сервиса.

Для проверки реальной доставки E009 оператор использует отдельные тестовые credentials,
контролируемые им адреса и ограничение получателей на стороне транспорта. Такая проверка
не включает штатную внешнюю доставку для произвольного тестового дневника. После неё
тестовое окружение возвращается к перехвату. Полученные OAuth-профили тестовых аккаунтов
не используются как рабочий дневник и не выгружаются в фикстуры репозитория.

## Проверочные проходы для S02

| Действие | Ожидаемый наблюдаемый результат |
|---|---|
| Чистый локальный запуск по инструкции | Нужны только описанные локальные параметры; рабочая БД и кабинеты не требуются |
| Создать атлета и тренировку в test, затем открыть prod | В prod этих данных нет; test не может подключиться к рабочей PostgreSQL своей ролью и сетью |
| Перезапустить/переустановить test | Рабочий том и дневники не меняются; собственные тестовые данные сохраняются при обычном повторном развёртывании |
| Запросить восстановление в test на настоящий адрес | Во внешнюю почту ничего не доставляется; тестовое письмо перехвачено, рабочие credentials отсутствуют |
| Передать callback тестового провайдера на рабочий origin | Не создаются рабочий атлет и сессия; попытка не относится к этому окружению |
| Запустить обычную проверку изменения | Нет рабочих секретов, SSH-ключа и разрешения на развёртывание; проверка воспроизводима |
| Проверить образ SPA и диагностический вывод | Нет паролей, токенов и содержимого личного дневника |
| Открыть калькулятор при рабочей сессии | Нет запроса API/сессии и передачи собственного веса из дневника |

Это проект проверок, а не отчёт о запущенных окружениях. T002 можно принять полностью
после входов T001 и подтверждения возможности подключения выбранных внешних сервисов;
работающие интеграции проверяются уже в E006/E009/E010. Проверки типов и тесты приложения
здесь неприменимы: исходный код, зависимости и конфигурация не создаются.
