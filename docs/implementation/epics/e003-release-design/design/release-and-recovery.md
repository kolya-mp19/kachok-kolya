# Выпуск и восстановление

Проектный результат [E003-T004](../tasks/t004-release-and-recovery.md).
Входы — [окружения](./environments-and-access.md), [аудитория](./audience-and-constraints.md),
[сохранность ввода](../../e001-technical-design/design/input-preservation.md)
и [стек E001](../../e001-technical-design/design/technology-stack.md).
Здесь выбраны процедуры для владельца и нескольких знакомых с минимальной нагрузкой.
Механизм копирования, автоматизация и инфраструктура ещё не созданы.

## Ответственность и единица выпуска

Оператор — владелец, сопровождающий систему по инструкции. Он выполняет выпуск
в отдельное короткое окно обслуживания; непрерывная доступность одного сервера
не обещается. Решение об открытии конкретной версии аудитории принимает владелец
в E030 после E028/E029. Документирование процедуры не означает такого решения.

Выпуск идентифицируется commit SHA, неизменяемыми digest образов API и статики,
версией PostgreSQL/Prisma, набором миграций и версией несекретной конфигурации.
Секреты передаются отдельно по T002. E004 фиксирует совместимые версии и команды,
E006 — проверяемый маршрут выпуска. Образы собираются один раз и продвигаются
из test в prod без повторной сборки; секретов в образах нет. Сохраняется предыдущий
набор образов и совместимая конфигурация, а не только изменяемый тег latest.

## Последовательность выпуска

| Этап | Действие | Условие продолжения |
|---|---|---|
| Проверки | Выполнить проверку типов, предметные и интеграционные тесты затронутых эпиков, затем полную обязательную suite и сборку API/SPA; проверить отсутствие секретов в артефактах | Все обязательные проверки успешны, сборка идентифицируема |
| Репетиция в test | Применить миграции к чистой и заполненной синтетической БД, выполнить контрольный мобильный проход; повторить применение и запуск | Данные сохраняются; повтор не повторяет миграции и факт, почта перехвачена |
| Подготовка prod | Проверить свободный диск, доступы и конфигурацию без печати значений, наличие образов и проверенного пути возврата; сообщить знакомым об окне | Определены оператор, совместимость схемы и ветвь действий при сбое |
| Остановка изменений | Перевести дневник в обслуживание на reverse proxy; остановить API и календарный обработчик, дождаться завершения активных транзакций | Новые команды не принимаются и фоновые изменения не идут; калькулятор может оставаться доступным статически |
| Предварительная копия | Создать полный дамп БД и комплект восстановления, зашифровать, вынести за сервер и проверить целостность | Есть успешный комплект с границей данных перед изменением схемы; ошибку копирования нельзя пропустить |
| Миграция | Отдельным одноразовым процессом применить готовые миграции из выпуска с ролью мигратора | Известны код завершения и фактически применённые миграции; приложение ещё не принимает запись |
| Установка | Запустить согласованный образ API и статики с нужной конфигурацией; проверить готовность БД/API и прямые ссылки SPA | Готовы приложение и схема, старый интерфейс не обслуживается как новая сборка |
| Проверка | Проверить HTTPS, калькулятор без API, вход контрольного владельца, чтение плана/факта и изоляцию второго дневника; безопасную запись проверить на отдельном контрольном дневнике | Истинные данные не используются для тестовой отметки; исходящий почтовый smoke идёт только контролируемому получателю |
| Открытие | Снять обслуживание, проверить повтор чтения/записи и календарное приведение пропущенного времени; записать результат выпуска | Новая версия обслуживает согласованную аудиторию, известны версия и состояние копии |

На чистой установке рабочего дневника ещё нет: БД создаётся пустой, миграции
применяются до API, контрольные атлеты создаются разрешённым потоком.
Рабочий том не удаляется ради повторного запуска. Миграции не выполняются
конкурентно каждым экземпляром приложения.

Для Prisma v7 штатное применение готовых миграций — `prisma migrate deploy`;
команда сама не ищет drift и не заменяет тест миграции. E004 закрепляет CLI
соответствующей выбранной версии; смена версии требует проверить команды.
Основание: [Prisma deploy](https://docs.prisma.io/docs/cli/v7/migrate/deploy).
В prod не используются reset, разработческая генерация миграций или принудительное
приведение схемы без проверенного SQL-плана.

## Неуспех и совместимость схемы

| Момент сбоя | Действие |
|---|---|
| Проверка, сборка или test неуспешны | Остановить выпуск; prod не менять |
| Конфигурация или предварительная копия не готовы | Не выполнять миграцию; вернуть прежний API и снять обслуживание после проверки |
| Миграция завершилась частично | Оставить обслуживание; сохранить диагностику, определить фактическую схему и историю миграций; применить заранее проверенное исправление вперёд либо восстановить предварительную копию в отдельную БД |
| Схема совместима с прежним API, новый API не готов | Вернуть предыдущие образы и конфигурацию, проверить данные и открыть прежнюю версию без восстановления БД |
| Схема несовместима, исправление вперёд не проходит | Восстановить предварительную копию в новую БД с прежними образами; проверить комплект и переключить подключение только после приёмки |
| Дефект обнаружен после открытия записи | Снова закрыть запись; сохранить текущую БД для разбора. Сначала искать совместимый возврат кода/исправление вперёд; восстановление старой копии требует учесть все подтверждённые после неё изменения |

Каждая миграция имеет в описании выпуска ожидаемую схему, совместимые образы,
контрольные запросы и проверенный путь неуспеха. Добавление нового поля выполняется
сначала совместимым расширением и заполнением, смена читателя/писателя — отдельным
шагом; удаление старого поля допускается после проверки нового чтения и копии.
Если такой порядок неприменим, изменение проходит в окне без записи с репетицией
восстановления. Произвольный обратный SQL не считается гарантированным откатом.

При частичной миграции запись статуса через Prisma resolve разрешается только после
сверки действительной схемы с проверенным планом; отметка «применено» сама не выполняет
недостающий SQL. История и исправление возвращаются в репозиторий. Основание:
[Prisma: failed migrations](https://www.prisma.io/docs/orm/v7/prisma-migrate/workflows/patching-and-hotfixing).

## Состав и параметры копий

Для небольшой БД выбран полный логический дамп PostgreSQL в custom-формате
через `pg_dump -Fc` с восстановлением `pg_restore` в чистую БД. Он даёт согласованный
снимок одной БД; глобальные роли им не копируются. Роли и полномочия воспроизводятся
отдельной инструкцией с новыми секретами. Копирование работающего каталога тома
без согласованного механизма PostgreSQL не используется.
Основание: [PostgreSQL SQL Dump](https://www.postgresql.org/docs/current/backup-dump.html),
[pg_dump](https://www.postgresql.org/docs/current/app-pgdump.html).

| Параметр | Проектное решение |
|---|---|
| Состав БД | Все схемы приложения и миграции, атлеты и способы входа, подтверждённая почта, хеши паролей, план/факт, даты, связи упражнений, исторические условия, источники и пересмотры МПВ, собственный вес, производные результаты, квитанции и ключи локальных черновиков |
| Остальной комплект | Манифест версии/схемы и контрольной суммы, инструкция восстановления ролей/расширений, ссылки на неизменяемые образы, несекретная конфигурация; отдельный зашифрованный архив действующих секретов и доступа к внешним кабинетам в хранилище владельца |
| Периодичность | Автоматически каждый час; дополнительно перед каждым изменением схемы и конфигурации, влияющей на доступ/расшифровку |
| Размещение | Зашифрованная копия вне рабочего физического сервера, в закрытом хранилище владельца; локальный временный файл не считается готовой копией. Ключ расшифровки и восстановление доступа не должны зависеть только от рабочего сервера |
| Хранение | Все часовые комплекты за 48 часов, один полный комплект за сутки за 14 суток; предварительные комплекты выпуска — 14 суток. Секреты соответствующей версии сохраняются на тот же срок отдельно и зашифрованно |
| Допустимая потеря | Целевой RPO — не более 2 часов подтверждённых сервером данных при отказе сервера. Возраст считают от начала согласованного снимка последней успешно вынесенной и проверенной копии, а не от времени загрузки файла |
| Срок восстановления | Целевой RTO — не более 4 часов от начала процедуры оператором с доступным резервным местом запуска и ключами до проверенного открытия дневника. Ожидание реакции владельца и получение нового сервера учитываются отдельно; круглосуточного срока устранения аварии нет |
| Контроль | После каждого запуска проверяются exit code, размер, манифест, checksum после передачи и читаемость архива; каждые 15 минут — возраст последней успешной вынесенной копии. При возрасте более 90 минут или ошибке оператор получает уведомление без личных записей |
| Проверка восстановления | До выпуска в E029, затем ежемесячно и после изменения механизма копирования, схемы, PostgreSQL или критичных секретов |

Параметры выбраны как проектные ограничения для небольшого числа атлетов,
а не как измеренные гарантии. E029 подтверждает их фактическим восстановлением;
при несоответствии исправляются механизм или проект до выпуска. При возрасте
копии свыше 2 часов оператор останавливает приём новых записей до получения
пригодной копии; отсутствие дежурства означает остаточный риск поздней реакции.
Успешная проверка checksum не заменяет восстановления. Удаление старых комплектов
выполняется только после получения новой успешной копии; неудачный запуск не должен
сначала удалить последний пригодный комплект.

Неотправленные черновики IndexedDB не входят в серверную копию. Ключи их расшифровки
входят в БД; потеря ключа, созданного после границы копии, может сделать соответствующий
локальный черновик нечитаемым. Нельзя обещать восстановление этого ввода из дампа.
Сессии, одноразовые токены и пароли из восстановленной БД не активируются повторно.

## Процедура восстановления

1. Закрыть запись и фоновые обработчики; сохранить аварийную БД/том для разбора,
   определить причину, границу данных и выбранный комплект. Не стирать рабочий том.
2. Проверить манифест, checksum и расшифровку, наличие совместимых образов, версии
   PostgreSQL, инструкции ролей и секретов. В E029 утилиты сверяются с выбранной
   версией PostgreSQL; major upgrade не совмещается с аварийным восстановлением.
3. Поднять отдельный закрытый Compose-проект восстановления с новой БД/сетью/томом
   и ограниченным доступом оператора. Это отдельное окружение с личными данными,
   обычный test остаётся синтетическим. Исходящие почта/OAuth и календарь отключены.
4. Восстановить роли/расширения и полный архив БД, проверить ошибки восстановления,
   схему и миграции. Подключить совместимую версию API в режиме обслуживания.
5. Серверным изменением состояния отозвать все восстановленные сессии,
   одноразовые токены и отложенные письма; удалить все восстановленные хеши паролей
   из активных записей способов входа,
   чтобы не оживить истёкшие/использованные доступы и не отправить письма повторно.
   Выполнить это до открытия любых маршрутов входа восстановленного сервиса;
   при ошибке оставить сервис в обслуживании. Удаление хешей сохраняется в БД
   и не отменяется перезапуском. Сам архив копии не изменяется.
   Вход по почте требует нового письма восстановления и установки нового пароля
   в существующий дневник. Новые письма выпускаются только после очистки старых
   токенов и проверки доставки на контролируемом адресе. До готовности доставки
   вход по паролю остаётся закрытым; подключённые провайдеры сохраняются.
   Очистка cookie браузера не заменяет отзыв на сервере. Ключи черновиков сохранить;
   не создавать новые под старыми идентификаторами.
6. Выполнить контроль данных ниже. Зафиксировать время начала/окончания, границу
   восстановленных данных и фактическую потерю по журналу инцидента без публикации
   личного содержимого. Несоответствие RPO/RTO явно фиксируется, а не скрывается.
7. Перед открытием сменить поколение восстановления по правилу ниже; проверить
   вход владельца, безопасное повторение и календарное приведение к текущей дате.
8. Переключить рабочую конфигурацию на проверенную БД; исходящую доставку включить
   только для новых разрешённых действий. Открыть доступ, получить новую внешнюю
   копию и сообщить знакомым границу восстановленных данных. Аварийная БД остаётся
   закрытой для разбора и согласования потерянных подтверждённых записей.

## Повтор команд после восстановления старого снимка

Восстановление может удалить квитанцию уже выполненной операции и вернуть старую
редакцию объекта. Одного отзыва сессий недостаточно: после нового входа прежний
envelope не должен автоматически примениться повторно к откатившейся редакции.

Для E005/E019 вводится идентификатор поколения восстановления: случайное значение
конфигурации сервиса вне восстанавливаемой БД, неизменное при обычном выпуске и
новое при возврате данных к прежнему снимку. Сервер сообщает поколение после входа;
envelope и квитанция включают его в проверяемые поля. Сервер отвергает старое
поколение до применения операции и проверки квитанции, возвращая явный код
«Состояние восстановлено, сверьте дневник» без изменения данных. Браузер сохраняет прежний
черновик, показывает необходимость сверить восстановленный дневник и не переписывает
поколение внутри уже отправленной неизменяемой команды. После сверки атлет явно
создаёт новую команду по актуальному состоянию. Старый интерфейс без поддержки
поколения не получает права записи, а предлагает обновиться.

Это уточнение протокола E001 для аварийного возврата БД, а не смена идентификаторов
при каждом выпуске. Проверка в E005/E029: команда подтверждена после снимка, затем
БД восстановлена; повтор старого envelope после нового входа не меняет данные.
Контрольный новый envelope нового поколения применяется один раз. Локальные
данные другого атлета по-прежнему недоступны; восстановление не отменяет изоляцию.

## Контроль дневника и передача в E029

Приёмочный комплект содержит два синтетических дневника А/Б и контрольные записи:
ручной план без МПВ; фиксированный план и отличный от него факт; разминку; копию
без весов; действительную и планируемую даты; исправленную проходку; связь личного
упражнения с системным; исторические условия; собственный вес и ключ черновика.
До снимка записываются ожидаемые значения по [матрице T003](../tasks/t003-acceptance-matrix.md).

После восстановления сверяются исходные значения и владельцы, фиксированность
плана, история исправлений, МПВ и показатели; текущие личные свойства упражнения
не подменяют исторические условия. Пересчёт выполняется штатным механизмом E001,
его результат сравнивается с ожидаемым. А не читает Б; прежний ciphertext А доступен
только А после входа, если ключ существовал в снимке. Восстановленные токены не
действуют; старая команда не применяется после смены поколения.

Отдельный контроль доступа: установить пароль А, сделать снимок, затем штатно
сменить пароль на Б и восстановить снимок. После подготовки восстановления
ни А, ни Б не создают сессию; повторить проверку после перезапуска. Старая ссылка
восстановления также не действует. Новое письмо на подтверждённую почту позволяет
установить пароль В и войти в тот же дневник; повтор ссылки отклоняется, А и Б
остаются недействительными. Проверить дневник без провайдера и с подключённым
провайдером: вход через провайдера не возвращает действительность прежнему паролю.

[E029-T002](../../e029-operational-readiness/tasks/t002-backup-restore.md) получает
весь состав, расписание, внешнее зашифрованное хранение, удержание, RPO/RTO,
контроль возраста и процедуру. Она настраивает штатный механизм и проверяет полную
версию; E006 получает выпуск и контроль миграций, E005 — поколение восстановления,
E030 — условия допуска. До фактического прогона ни работающие копии, ни выполненные
целевые времена не заявляются. Тесты приложения в этой задаче не запускались:
результат состоит из документов, проверяются сценарии и ссылки.
