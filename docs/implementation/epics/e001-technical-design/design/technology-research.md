# Исследование технической основы

Вход для [T005](../tasks/t005-technology-stack.md), а не самостоятельное согласование
стека. Окончательная проверка выполняется после [T001](../tasks/t001-constraints.md) и [T004](../tasks/t004-history-recalculation.md). Здесь проверены возможности
технологий; навыки владельца, бюджет и доступность конкретного размещения из этого
исследования не следуют. Приложение и зависимости не создаются.

## Рекомендуемый вариант

JavaScript-экосистема: TypeScript, React SPA со сборкой Vite, NestJS как модульный
монолит, Prisma ORM и одна PostgreSQL для постоянных данных. Приложение размещается
на одном сервере через Docker Compose — это подтверждённое ограничение владельца. Готовые компоненты
Ant Design, Tailwind CSS для компоновки. Это инженерная рекомендация по требованиям
владельца, которую T005 проверяет на сценариях модели и ограничениях эксплуатации.

TypeScript добавляет проверку типов к JavaScript, сохраняя его возможности;
Nest поддерживает оба языка. Предлагается TypeScript ради контрактов операций и
различения плана, факта и производных результатов. Цена — настройка компиляции и
обучение типам; проверка типов не заменяет проверку входящих данных во время выполнения.
TypeScript подтверждён владельцем в [ограничениях](./constraints.md). Основания: [TypeScript для JS-разработчиков](https://www.typescriptlang.org/docs/handbook/typescript-in-5-minutes.html),
[введение Nest](https://docs.nestjs.com/), [валидация Nest](https://docs.nestjs.com/techniques/validation).

## Сравнение архитектур

| Вариант | Преимущества для этого продукта | Цена и ограничения | Вывод |
|---|---|---|---|
| NestJS + React SPA/Vite | Явная граница API; модули, внедрение зависимостей и обработка запросов по соглашениям; интерфейс публикуется статическими файлами | Две сборки; маршрутизацию, загрузку данных и ошибки SPA нужно организовать отдельно; первоначальная загрузка зависит от JS и API | Основной кандидат: личному дневнику не требуется SSR, а календарь и пересчёт всё равно принадлежат серверу |
| Next.js с серверными возможностями | Маршруты, серверное получение данных, SSR/SSG и оптимизации интегрированы | При добавлении Nest появляются два серверных слоя; без Nest серверную архитектуру и обработку фоновых переходов пришлось бы проектировать внутри Next | Нет текущей потребности в серверном рендеринге, оправдывающей дополнительный слой |
| Next.js со статическим экспортом + Nest | Может выпускать HTML/CSS/JS без сервера Next; оставляет путь к серверным функциям позднее | Экспорт ограничен возможностями, вычисляемыми при сборке; серверные функции недоступны; для произвольных личных маршрутов нужно учитывать ограничения экспорта | Допустим, но Vite проще соответствует выбранной границе SPA/API |
| React SPA + Express/Fastify без Nest | Меньше соглашений и служебного кода в небольшом API | Модули, обработку ошибок, доступ, валидацию и тестовые границы придётся стандартизировать самостоятельно | Реальная более лёгкая альтернатива; Nest предпочтителен при множестве связанных операций дневника |

Оценки простоты и соответствия — выводы для проекта. Фактические возможности описаны в
[Nest](https://docs.nestjs.com/), [рекомендациях React](https://react.dev/learn/build-a-react-app-from-scratch)
и [статическом экспорте Next.js](https://nextjs.org/docs/app/guides/static-exports).
React отдельно предупреждает: сборщик не решает маршрутизацию и получение данных;
выбор SPA переносит эту ответственность на проект.

Vite создаёт статический результат сборки; его сервер предварительного просмотра не
предназначен для рабочего размещения. Проект размещения должен отдавать файлы и
обрабатывать прямое открытие клиентских маршрутов. Предлагаемая топология — один
публичный origin: статика и `/api` через HTTPS на одном сервере под Docker Compose;
Nest остаётся единственным сервером бизнес-операций. Конкретный способ раздачи
и поставщика сервера определяет E003.
Основание: [размещение Vite](https://vite.dev/guide/static-deploy.html).

## PostgreSQL и Prisma

Одна реляционная БД позволяет сохранять факт, фиксацию плана и результат операции
в одной транзакции. PostgreSQL по умолчанию использует Read Committed; для конфликтующих
операций одного дневника проект должен явно задавать согласованность. Serializable
устраняет аномалии сериализации, но требует обработки отказов и повторов.
Основание: [изоляция PostgreSQL](https://www.postgresql.org/docs/current/transaction-iso.html).

В проверенной стабильной ветке Prisma 7 доступны интерактивная `$transaction`,
`isolationLevel: Serializable` и ошибка конфликта `P2034`. Приложение повторяет всю
транзакцию ограниченное число раз; внешние HTTP-вызовы и отправка писем не входят в неё.
Идемпотентность требует собственного ключа операции и ограничений уникальности;
ORM не делает произвольный запрос безопасным для повтора автоматически.
Основание: [транзакции Prisma 7](https://www.prisma.io/docs/orm/v7/prisma-client/queries/transactions.md).

Важна явная ветка документации: [статус Prisma](https://www.prisma.io/docs/orm/release-status)
помечает ORM 8 как release candidate, а [переход с ORM 7](https://www.prisma.io/docs/orm/coming-from-prisma-orm-7)
описывает существенно иной API и недостающие возможности. Поэтому будущий проект не
должен слепо устанавливать `latest` или смешивать примеры двух поколений. Выбран поддерживаемый стабильный выпуск; S02 фиксирует проверенные совместимые
версии и lockfile. Применение Prisma не требует Prisma Cloud или иной облачной БД.

Веса и проценты следует хранить точными десятичными значениями PostgreSQL и обрабатывать
через `Prisma.Decimal`; в JSON передавать десятичную строку, исключая неявное превращение
в двоичный `number`. Точность столбцов и округления определяются предметными правилами,
а не произвольными значениями в исследовании. Основание: [типы Prisma 7](https://www.prisma.io/docs/orm/v7/prisma-client/special-fields-and-types).

Prisma 7 разделяет создание миграций в разработке и применение готовых миграций при
выпуске. Рабочая база не использует `migrate dev`, `reset` или экспериментальный `db push`.
Миграции проходят просмотр SQL и проверку на отдельной базе. Откат приложения не равен
откату схемы: E003 должен задать проверяемый путь восстановления совместимых данных.
Основание: [миграции Prisma 7](https://www.prisma.io/docs/orm/v7/prisma-migrate/workflows/development-and-production).

PostgreSQL поддерживает логические копии, физические копии и непрерывную архивацию.
Выбор механизма зависит от согласованных допустимой потери данных и срока восстановления;
наличие PostgreSQL само по себе не подтверждает восстановимость.
Основание: [резервирование PostgreSQL](https://www.postgresql.org/docs/current/backup.html).

## Готовый UI и мобильный ввод

Ant Design предоставляет React-компоненты, типы и настройку темы; библиотека ориентирована
на веб-приложения. Это снижает объём самостоятельного создания полей, кнопок и сообщений,
но не подтверждает удобство конкретной тренировки с телефона. Предлагаются вертикальные
карточки и списки подходов, а не широкая таблица недели. E002 проверяет открытую клавиатуру,
нотацию, одно касание, правку на месте, фокус и длинные названия на реальных мобильных
браузерах. Основание о библиотеке: [Ant Design React](https://ant.design/docs/react/introduce/).

Ant Design и Tailwind совместимы при заданном порядке каскадных слоёв. Для Tailwind 4
официальный пример задаёт `theme, base, antd, components, utilities` и включает слой Ant
через `StyleProvider`. Тему компонентов задают токены Ant; Tailwind отвечает за внешнюю
компоновку. Не следует систематически переопределять внутренние селекторы компонентов.
Основание: [совместимость CSS Ant Design](https://ant.design/docs/react/compatible-style/).

Tailwind 4 требует современных браузеров: Chrome 111+, Safari 16.4+, Firefox 128+.
Матрица поддержки проекта должна удовлетворять одновременно Tailwind, Ant и React;
эти минимумы не являются обещанием поддержки всего приложения. Нужны отдельные проверки
на iOS Safari и Android Chrome по E003. Основание: [совместимость Tailwind](https://tailwindcss.com/docs/compatibility).

## Вход и границы стоимости

Яндекс описывает обмен кода OAuth и PKCE; официальный VK ID SDK показывает OAuth 2.1,
`state`, `codeVerifier` и необходимость регистрации приложения. Это совместимо с отдельным
сервером Nest и статическим интерфейсом; проект [T006](../tasks/t006-access-and-trust.md) должен определить серверные
проверки, сессию и явное подключение способов входа. Наличие SDK не подтверждает доступ
конкретного владельца к кабинету, модерацию приложения или доставку писем.
Источники: [Яндекс: код из URL](https://www.yandex.ru/dev/id/doc/ru/codes/code-url),
[официальный VK ID SDK](https://github.com/VKCOM/vkid-web-sdk).

Вариант не требует микросервисов, Redis, отдельной очереди или платного SSR-размещения.
Это проектное ограничение числа компонентов, а не оценка цены. Расходы включают выполнение
Node.js, PostgreSQL, хранение копий отдельно от основной БД, HTTPS/домен и доставку почты.
Docker Compose не обеспечивает сохранность при потере единственного сервера: данные БД должны переживать пересоздание контейнеров. Система копий по указанию владельца
сейчас не проектируется; условия восстановления остаются в E003/E029.
Цены, регион, конкретный поставщик сервера и цели восстановления нельзя признать согласованными
без результатов T001/E003. Модель T002–T004 проверена в [выбранной технической основе](./technology-stack.md).
