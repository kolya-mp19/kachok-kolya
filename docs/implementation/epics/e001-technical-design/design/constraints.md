# Ограничения технической основы

## Обязательные условия

| Условие | Основание | Как проверяем выбор |
|---|---|---|
| Экосистема JavaScript | Прямое указание владельца | Интерфейс и сервер используют Node.js/JavaScript; TypeScript рассматривается как средство статической проверки, а не другой исполняемый стек |
| Готовая библиотека интерфейса и Tailwind CSS | Прямое указание владельца; Ant Design приведён как пример | Проверить мобильный ввод и совместимость стилей; Tailwind отвечает за компоновку, компоненты — за элементы управления |
| Монолит и PostgreSQL | Прямое указание владельца | Один сервер приложения, одна основная реляционная БД; без микросервисов и обязательной распределённой инфраструктуры |
| Один сервер, Docker Compose | Подтверждено владельцем | Статика, API и PostgreSQL размещаются на одном сервере; запуск описывается одним Compose-проектом, без обязательного второго сервера |
| SSR не требуется | Прямое указание владельца | Сравнить React SPA и серверный рендеринг по сложности сопровождения и реальной пользе |
| При выборе NestJS использовать Prisma ORM | Прямое указание владельца | Проверить транзакции, миграции, конкурентные исправления и воспроизводимость пересчёта |
| Только документация в E001 | Задачи и инструкции репозитория | Не создавать проект, конфигурацию сборки, зависимости и инфраструктуру |
| Независимый калькулятор | [Карта контекстов](../../../../../CONTEXT-MAP.md) | Работает в памяти вкладки, без API, сессии и данных дневника |
| Ручной план без МПВ и сохранность ввода | [Принципы](../../../../principles.md), П1, П4 | Подсказки не блокируют ввод; потеря связи не очищает введённое |

## Предпочтения и принятый порядок работы

NestJS и React SPA выбраны после сравнения альтернатив в
[технической основе](./technology-stack.md). Ant Design принят как готовая библиотека
элементов управления; выбор не требует табличных интерфейсов на телефоне. Сопровождение одним владельцем — критерий сравнения
из [T005](../tasks/t005-technology-stack.md), но конкретные навыки не предполагаются.

Владелец поручил агентам самостоятельно разбирать технические вопросы, включая поиск
в первичных источниках. Это позволяет выбирать проектные механизмы; личный бюджет,
наличие внешних аккаунтов и доступное время сопровождения из этого не следуют.

## Входы E002 и E003

Из [E002](../../e002-mobile-experience/prd.md) получены обязательные сценарии:
экранная клавиатура и нотация, копия без весов, одно касание для отметки, правка истории,
раздельные состояния черновика и сохранённого факта, потеря связи и истечение сессии.
Их проверка в техническом проекте не завершает дизайн экранов E002. Библиотека UI должна
позволять карточки упражнений и компактные формы, не требуя десктопной таблицы.

Из [E003](../../e003-release-design/prd.md) получены ограничения: отдельные локальное,
тестовое и рабочее окружения; секреты вне git; тестовые письма не уходят реальным атлетам;
возврат версии отличается от восстановления БД; миграции требуют проверяемого пути
восстановления. Платный поставщик аутентификации не требуется: два заданных провайдера
и запасная почта остаются ответственностью приложения.

Для этих входов не требуется завершить E002/E003 целиком: технические механизмы
проектируются сейчас, а параметры выпуска и мобильная приёмка сохраняют своих владельцев.

## Подтверждённые условия сопровождения

Владелец подтвердил TypeScript в экосистеме JavaScript, доступность Docker Compose
и готовность сопровождать Node.js/PostgreSQL по воспроизводимой инструкции. Инструкция
должна покрывать чистый запуск, конфигурацию, миграции и диагностику без скрытых ручных шагов;
предыдущий опыт владения конкретным фреймворком не является условием выбора.

Бюджет и поставщик определяются в E003 перед настройкой инфраструктуры. Сейчас не
заказываются платные услуги и не предполагается бюджет. Один имеющийся сервер —
достаточное ограничение для сравнения числа обязательных компонентов.

Владелец отдельно исключил проектирование системы резервного копирования из текущей
работы. Не выбираются механизм, расписание и хранилище копий; значения RPO/RTO не
выдаются за проверенную гарантию. Это не отменяет требований [E003](../../e003-release-design/prd.md) и [E029](../../e029-operational-readiness/prd.md) до выпуска.
Открытых вопросов, блокирующих технический проект E001 в согласованном объёме, нет.

## Проверочные примеры

1. Кандидат требует SSR ради форм дневника: обязательной пользы нет, сравнивается стоимость
   второго серверного слоя и сопровождения; анонимный калькулятор остаётся статическим.
2. Кандидат требует Redis для каждой записи: проверить возможность сессий и повторов в
   PostgreSQL, чтобы не вводить второй обязательный сервис без необходимости.
3. Библиотека не сохраняет незавершённую нотацию при ошибке разбора: не удовлетворяет П4,
   даже если форма выглядит готовой.
4. Хостинг обещает резервные копии: без ответа на вопросы потери данных и восстановления
   это не доказательство соответствия условиям выпуска; проектирование копий выполняется позже.
