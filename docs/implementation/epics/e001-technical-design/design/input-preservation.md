# Сохранность ввода и повтор отправки

Проектный результат [T007](../tasks/t007-input-preservation.md) для выбранного
[стека](./technology-stack.md) и [серверной сессии](./access-and-trust.md).
Введённое сохраняется отдельно от факта. Только подтверждённая сервером операция
меняет дневник и показатели; потеря ответа не означает ни успех, ни отказ.

## Где находятся данные

| Данные | Место | Граница |
|---|---|---|
| Текущие поля, незавершённая нотация, частично введённая пара факта | Память React и зашифрованный черновик IndexedDB | Не являются фактом и не влияют на показатели |
| Неизменяемая подготовленная команда | Зашифрованная запись IndexedDB | Создаётся до отправки; повтор использует ту же команду и идентификатор |
| Сохранённые план, факт, условия и производные результаты | PostgreSQL | Источник подтверждённого состояния |
| Квитанция операции | PostgreSQL, тот же владелец | Сохраняется атомарно с результатом команды |
| Ключ защиты локального ввода | PostgreSQL; после авторизации — только память вкладки | Не записывается в IndexedDB, localStorage, sessionStorage или cookie |

Выбран IndexedDB, поскольку черновик должен переживать обычное закрытие вкладки.
Память вкладки и sessionStorage такой границы не дают. Черновик содержит исходный
текст, разобранную структуру при наличии, ошибки полей, идентификатор редактируемого
объекта, базовую серверную редакцию и собственную локальную редакцию. Синтаксическая
ошибка нотации не удаляет исходную строку и не заменяет сохранённый план.

Локальный идентификатор черновика различает независимые редакторы, в том числе
открытые в двух вкладках. Они не перезаписывают единственный общий слот тренировки.
При открытии того же объекта интерфейс предлагает продолжить найденный черновик
этого владельца, а не молча объединяет несколько разных правок. Согласованность
записей одного черновика обеспечивают транзакция IndexedDB и ожидаемая локальная
редакция; устаревшая запись не затирает новую.

Основания: [MDN: IndexedDB](https://developer.mozilla.org/en-US/docs/Web/API/IndexedDB_API/Using_IndexedDB),
[MDN: sessionStorage](https://developer.mozilla.org/en-US/docs/Web/API/Window/sessionStorage).

## Защита от другого аккаунта

Простого имени раздела с идентификатором атлета недостаточно: IndexedDB доступна
скрипту того же origin. Выбран небольшой механизм шифрования локального ввода,
без отдельного сервиса ключей и без синхронизации черновиков с сервером.
Для атлета сервер создаёт случайный ключ AES-256-GCM и его идентификатор, хранит
как личный секрет в PostgreSQL. Endpoint выдачи ключа получает владельца только
из действующей сессии, не принимает произвольного владельца, использует HTTPS
и `Cache-Control: no-store`. Другой аккаунт получает только свой ключ.

В браузере ключ импортируется Web Crypto как неэкспортируемый `CryptoKey` и остаётся
в памяти. Постоянно сохраняются только ciphertext, IV, идентификатор ключа и минимальные
непрозрачные идентификаторы. Содержимое полей, названия упражнений, комментарии,
полный envelope и сообщения валидации входят в шифротекст. AES-GCM использует новый
криптографически случайный 96-битный IV при каждом шифровании, без намеренного
повторного использования IV с тем же ключом. IV не выводится из номера редакции:
иначе разные вкладки или устройства могли бы повторить его. В additional authenticated
data входят версия формата, владелец, идентификатор ключа, черновика и редакция;
перестановка ciphertext между владельцами или записями не даёт успешной расшифровки.
Параметры IV и authenticated data основаны на [MDN: AES-GCM](https://developer.mozilla.org/en-US/docs/Web/API/AesGcmParams),
операции — на [Web Crypto encrypt](https://developer.mozilla.org/en-US/docs/Web/API/SubtleCrypto/encrypt).

Ключ загружается при открытии авторизованного дневника до начала сохраняемого
локального редактирования. После перезагрузки нужна сеть и действующая сессия,
чтобы снова получить ключ; открывать локальный дневник без сети не обещается.
Ключ переживает обычное истечение и восстановление сессии на сервере: это позволяет
тому же атлету прочитать прежний ciphertext. Смена пароля не создаёт нового владельца
и не уничтожает ключ автоматически. Потеря ключа делает оставшийся ciphertext
нечитаемым; ключ нельзя молча пересоздать под тем же идентификатором.

При `401`, выходе и смене аккаунта вкладка прекращает отправку, завершает шифрование
текущего ввода, скрывает личные поля, удаляет ссылки на ключ и открытые данные из
состояния интерфейса. Неподтверждённый ciphertext остаётся для прежнего владельца;
новый аккаунт не видит список его черновиков и не отправляет их под своей сессией.
Смена аккаунта/выход оповещает другие вкладки через BroadcastChannel без передачи
секретов. При возвращении вкладки из фона она сначала перепроверяет сессию; на каждую
отправку сервер также проверяет владельца envelope. Полученные после смены аккаунта
старые ответы отбрасываются по поколению клиентской сессии. Сами серверные команды
подчиняются отзыву и проверкам [T006](./access-and-trust.md).

Это защита сохранённого ввода от другого аккаунта приложения, а не сквозное шифрование:
сервер владеет ключом. XSS, вредоносное расширение, уже извлечённый в авторизованной
сессии ключ и доступ к памяти устройства находятся вне этой гарантии. Неэкспортируемость
CryptoKey не спасает от скрипта, способного вызвать расшифровку в живой вкладке.
Шифрование также не заменяет очистку DOM и проверку владельца на сервере.

## Локальное сохранение и состояния интерфейса

Каждое изменение немедленно остаётся в памяти; запись актуальной редакции в IndexedDB
запускается последовательно, чтобы позднее окончание шифрования не вернуло старую
редакцию. Статус «Черновик на устройстве» появляется после `complete` транзакции
IndexedDB, а не после успеха одного запроса записи. До этого показывается
«Сохраняем черновик». Перед отправкой неизменяемый envelope и ссылка на его локальную
редакцию должны пройти эту же границу.
Основание: [MDN: завершение транзакции](https://developer.mozilla.org/en-US/docs/Web/API/IDBTransaction/complete_event).

| Состояние | Что видит атлет | Что разрешено |
|---|---|---|
| Незавершённый ввод | Поля/нотация и ошибки разбора; отдельно прежний факт | Исправлять ввод; показатели прежние |
| Черновик на устройстве | «Не отправлено» | Отправить допустимую команду при доступной сессии |
| Отправляется | «Сохраняем» у конкретного действия | Не считать подход сохранённым; не создавать повторную команду вторым нажатием |
| Результат неизвестен | «Ответ не получен. Проверить и повторить» | Проверить ту же операцию после восстановления доступа |
| Нужен вход | «Войдите, чтобы продолжить»; личный ввод скрыт | Войти тем же аккаунтом; ciphertext сохраняется |
| Конфликт/ошибка | Понятное объяснение рядом с сохранённым вводом | Сверить актуальный серверный объект и явно исправить команду |
| Подтверждено | Факт и редакция из серверного подтверждения | Очистить только соответствующую подтверждённую локальную редакцию |

Представления передаются в [E002](../../e002-mobile-experience/prd.md): план, черновик
факта и сохранённый факт различаются текстом/значком, а не только цветом. Потеря сети
не снимает введённое с экрана и не рисует подтверждённую отметку. После `401` применяется
граница приватности выше; возвращение того же атлета восстанавливает поля.
Одно касание для подхода остаётся одним пользовательским действием: подготовка
локальной записи и отправка выполняются внутри него без дополнительной кнопки.

## Неизменяемая команда и серверная квитанция

Envelope содержит версию протокола, случайный UUID операции, ожидаемого владельца,
вид команды, идентификаторы объектов, ожидаемую серверную редакцию и полный payload
с явной фактической датой. Пароли, session token и CSRF-токен в envelope не входят.
CSRF-заголовок берётся из текущей сессии при каждой попытке отправки.
После первой отправки envelope не меняется. Сервер сам вычисляет хеш канонически
представленных значимых полей: порядок ключей JSON не считается различием,
ожидаемая редакция и фактическая дата считаются. Хеш из браузера не является доказательством.

Владелец envelope — дополнительная проверка, а не способ назначить владельца:
он обязан совпасть с владельцем действующей сессии. Ключ квитанции — пара
`(athleteId, operationId)`. Квитанция содержит хеш команды, результат, присвоенные
идентификаторы и подтверждённую редакцию. Не содержит секретов доступа. Первая
версия не удаляет квитанции успешных команд, пока существует соответствующий дневник:
повтор старого неопределённого запроса не теряет защиту из-за произвольного TTL.

Одна серверная операция:

1. Проверить сессию, CSRF и совпадение ожидаемого владельца. Получить ту же блокировку
   владельца, что календарь и пересчёт; повторно проверить действительность доступа.
2. Найти квитанцию этого владельца и UUID **до проверки ожидаемой редакции**.
   При совпавшем хеше вернуть исходное подтверждение без применения команды заново.
   При другом хеше вернуть конфликт идентификатора, не менять данные.
3. Если квитанции нет, привести календарь к дате БД, проверить редакцию и все доменные
   условия. Старую допустимость даты нельзя предполагать только по локальному черновику.
4. В одной транзакции применить всю команду: при первом факте — фиксацию всей тренировки,
   необходимые условия/разминку, факт и согласованные производные результаты. Для других
   видов команды использовать их границы T002–T004.
5. В той же транзакции записать уникальную квитанцию и подтвердить всё вместе;
   только затем вернуть успех. При сбое откатить и изменения, и квитанцию.

Блокировка и ограничение уникальности предотвращают две конкурентные команды с одним
UUID. Факт также привязан к устойчивому идентификатору планового подхода, но это не
заменяет квитанцию: повтор более старого исправления не должен затереть новое.
Повтор подтверждённой операции возвращает её историческую редакцию; клиент не выдаёт
её за самое свежее состояние, если последующие изменения уже известны. При необходимости
перечитывает актуальный объект и показывает сохранённый результат отдельно.

`401`, ошибка валидации и конфликт не считаются успехом и не очищают ввод.
Неуспех с откатом не создаёт квитанцию успешной записи. После окончательного отказа
атлет исправляет ввод и явно создаёт новую команду с новым UUID. После timeout, обрыва
или технического `5xx` результат сначала остаётся неизвестным: прежнюю команду нельзя
пересоздать под новым UUID до проверки исходного результата. Проверка квитанции
доступна только тому же владельцу. Если квитанции пока нет, безопасно повторить
тот же envelope: серверная блокировка сериализует его с возможным первым запросом.

## Ответы, новые правки и ручной повтор

Для одного изменяемого корня разрешён максимум один неразрешённый отправленный
envelope в конкретном редакторе. Атлет может исправлять текущие поля во время
ожидания, но новая редакция остаётся черновиком; её нельзя отправить раньше
уточнения исходной операции. Это не очередь фоновых команд.

При успехе клиент в одной локальной транзакции помечает envelope подтверждённым
и удаляет черновик **только если** его текущая редакция совпадает с отправленной.
Если после отправки редакции 5 атлет набрал редакцию 6, подтверждение 5 оставляет 6
и её текст. Она сохраняет исходную базовую серверную редакцию: при изменении базы
нужна явная сверка с новым серверным состоянием, не молчаливое снятие конфликта.
Сбой очистки после успеха безопасен: сохранившийся envelope при повторе найдёт ту же
квитанцию. Старый ответ другого UUID или другого поколения сессии не очищает данные.

После потери связи сохраняется конкретный уже введённый черновик. Нет фоновой
доставки при появлении сети, service worker, кэша всего дневника, создания новых
тренировок без сервера или синхронизации устройств. Возвращение сети предлагает
«Проверить и повторить»; атлет явно продолжает отправку. Для истёкшей сессии сначала
нужен вход: тот же атлет получает свой ключ, проверяет квитанцию и повторяет исходную
команду при необходимости. Вход другим способом в тот же аккаунт подходит.

## Закрытие вкладки и ошибки хранилища

Обычное закрытие после `complete` оставляет ciphertext и envelope в IndexedDB.
При следующем сетевом открытии того же аккаунта восстанавливается черновик;
незавершённая отправка показывается как неизвестный результат. Необработанное
последнее нажатие до завершения локальной транзакции пережить закрытие не обязано;
`beforeunload` не является механизмом записи. Очистка сайта, приватный режим,
вытеснение браузером и отказ устройства могут удалить даже завершённую запись.
Успешная транзакция браузера не равна гарантии против внезапной потери питания.

Приложение запрашивает persistent storage как улучшение сохранности, но отказ не
выдаёт за успешное предоставление гарантии. При недоступной IndexedDB, переполнении,
ошибке шифрования или записи ввод остаётся в памяти, показывается «Черновик пока
только в этой вкладке». Отправка до сохранения envelope не начинается; атлет может
повторить локальную запись. При auth failure текущий ввод шифруется до очистки
памяти; если запись IndexedDB не удалась, ciphertext временно остаётся только в памяти
заблокированной вкладки, без ключа и открытых полей. После повторного входа того же
атлета его можно восстановить, но закрытие вкладки в таком состоянии потеряет ввод.
Ошибка не замалчивается и не удаляет ранее сохранённый факт на сервере.

Основания: [MDN: хранение и вытеснение](https://developer.mozilla.org/en-US/docs/Web/API/Storage_API/Storage_quotas_and_eviction_criteria),
[MDN: надёжность транзакции IndexedDB](https://developer.mozilla.org/en-US/docs/Web/API/IDBTransaction).
Штатное резервное копирование сервера по указанию владельца здесь не проектируется.

## Проверочные последовательности

| Последовательность | Где данные и что видит атлет |
|---|---|
| Введён только вес, сеть пропала до отправки | Незавершённая пара в памяти/зашифрованном черновике, прежний серверный факт не изменён; виден «Не отправлено» |
| Команда сохранена локально, запрос не дошёл | Envelope остаётся, квитанции нет; ручной повтор того же UUID создаёт одну запись |
| Сервер подтвердил транзакцию, ответ потерялся | Факт и квитанция в PostgreSQL, envelope в IndexedDB; повтор возвращает исходный результат без второй фиксации/подхода |
| Два одновременных запроса одного UUID | Общая блокировка и уникальность дают один результат; второй получает ту же квитанцию |
| Тот же UUID отправлен с новым весом | Хеш другой, конфликт идентификатора; сохранённый факт не меняется |
| Редакция 5 отправлена, во время ожидания введена 6 | Ответ 5 не удаляет 6; сервер подтверждает только 5, 6 остаётся черновиком для сверки |
| После операции А другой запрос Б изменил объект, затем повторена А | Историческая квитанция А возвращена без повторной записи; UI не заменяет известную более новую редакцию Б |
| `401` до записи или при повторе после потерянного ответа | Ввод зашифрован и скрыт, envelope сохранён; вход тем же атлетом → проверка квитанции → ручной повтор при отсутствии |
| Аккаунт А вышел, вошёл Б | Б не получает ключ А, не видит/не отправляет его черновик; ожидаемый владелец А не принимается с сессией Б |
| Закрыта вкладка после локального `complete`, ответа сервера нет | После входа тем же атлетом envelope восстановлен как «Результат неизвестен»; нужна проверка, не новый UUID |
| Браузер удалил хранилище | Несохранённого на сервере ввода может не быть; подтверждённый дневник по-прежнему читается из PostgreSQL |
| Конкурирующая правка/календарная граница изменила редакцию | Команда получает конфликт, текст остаётся; новый серверный объект сверяется явно, старый план не открывается |
| Сервер упал до commit | Ни факта, ни квитанции нет; тот же UUID применяется при повторе один раз |
| Квитанция получена, локальная очистка упала | Повтор находит квитанцию; черновик очищается по редакции, нового подхода нет |
| В IndexedDB превышена квота | Ввод в памяти, явная ошибка локальной сохранности; сеть не отправляет неподготовленный envelope |

Диагностика сообщает вид операции, код ошибки и непрозрачный идентификатор без
тела команды, ключей, токенов, адресов, нотации, факта и комментариев. Ошибка расшифровки
не удаляет ciphertext автоматически и не приводит к отправке повреждённых данных.

## Проверка критериев T007

|---|---|
| Место, состояния и очистка | Таблицы хранения/интерфейса, локальные редакции и условие удаления |
| Повтор без второго подхода | Неизменяемый envelope, квитанция до проверки редакции, единая транзакция |
| Потеря запроса/ответа, истечение и вход | Проверочные последовательности и ручное продолжение тем же владельцем |
| Закрытие и другой аккаунт | Ciphertext IndexedDB, серверная выдача ключа, очистка памяти и реальные границы браузерного хранения |
| E002 и диагностика | Различимые состояния плана/черновика/факта, русские тексты, ошибки без личного содержимого |
| Нет полного оффлайна | Нет фоновой очереди, кэша дневника и синхронизации; повтор только конкретной команды |

Пройдены последовательности документа; автоматические тесты и проверка типов
неприменимы до появления приложения. В E005/E019 будущие интеграционные проверки
используют разрыв запроса/ответа, реальные транзакции, две сессии, закрытие вкладки
и конфликт редакций. Проект не объявляет мобильные макеты E002 или эксплуатацию E003 готовыми.
