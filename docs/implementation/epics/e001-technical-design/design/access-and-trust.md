# Доступ к одному дневнику и границы доверия

Проектный результат [T006](../tasks/t006-access-and-trust.md) для выбранных
[NestJS, React SPA, Prisma и PostgreSQL](./technology-stack.md). Сначала Яндекс,
затем ВКонтакте; почта с паролем — обязательный запасной способ. У атлета один
идентификатор и один дневник, способов входа может быть несколько. Код и подключение
внешних сервисов здесь не создаются.

## Границы доверия и операции

Браузер доверенным источником владельца не является. React передаёт команды, NestJS
проверяет их, а PostgreSQL хранит владельца, источники и результаты. SPA и API работают
через один HTTPS origin; БД не доступна из интернета. Секреты провайдеров находятся
только на сервере. Доверие к заголовкам reverse proxy ограничено этим proxy; входящий
пользовательский заголовок не может назначить IP, HTTPS или идентификатор атлета.

| Операция | Доказательство и проверка |
|---|---|
| Получить дневник, цикл, план, факт или историю | Действующая серверная сессия; запрос ограничен её владельцем |
| Читать и менять личные упражнения, связи, настройки, залы | Тот же владелец у корня и всех переданных личных ссылок; системный справочник доступен для чтения |
| Читать и менять разминку, собственный вес, RPE и комментарии | Та же проверка владения, включая вложенные идентификаторы |
| Читать показатели, МПВ, динамику и результаты пересчёта | Производные записи также ограничены владельцем; общий идентификатор упражнения не даёт чужую историю |
| Записать факт, исправить условия, прервать цикл, повторить команду | Сессия, CSRF, владение, ожидаемая редакция; квитанция повтора принадлежит тому же владельцу |
| Запустить календарь или пересчёт без браузера | Внутренняя серверная операция с явно выбранным владельцем и общим порядком блокировок; не публичный маршрут обхода доступа |
| Подключить способ входа | Свежие доказательства существующего аккаунта и нового провайдера в одной попытке подключения |

Guard NestJS закрывает маршруты дневника по умолчанию. Сервис операции повторно
ограничивает запрос владельцем: один guard без проверки принадлежности объекта
недостаточен. Вложенный подход проверяется через упражнение, тренировку, неделю и цикл;
выбранный личный зал или комплекс тоже должен принадлежать этому атлету. Списки,
поиск, пакетные команды и предварительные просмотры подчиняются тому же правилу.
Чужой и отсутствующий объект дают одинаковый ответ «Не найдено» без его содержимого.

Анонимны только статический калькулятор, необходимые операции входа/подтверждения
и чтение действительно общих справочников. У калькулятора отдельная клиентская точка:
она не загружает сессию, не вызывает API и не читает хранилище дневника. Успешный вход
не переключает калькулятор в дневник без явного действия атлета.

## Логические записи доступа

| Запись | Назначение и ограничение |
|---|---|
| Атлет | Устойчивый идентификатор, имя, адрес восстановления, дата регистрации, редакция доступа; дневник принадлежит этому идентификатору |
| Способ входа провайдера | Атлет, код провайдера, устойчивый `subject`; уникальная пара `(provider, subject)` |
| Пароль | Необязательный Argon2id-хеш с индивидуальной солью у существующего атлета; plaintext не хранится |
| Сессия | Хеш случайного 256-битного токена, атлет, время создания и активности, абсолютное истечение, признак отзыва |
| Попытка OAuth | Хеш случайного `state`, браузерная привязка, конкретный провайдер, цель «вход / подключение», срок, PKCE verifier и при подключении целевой атлет |
| Ожидающее подтверждение | Назначение токена, хеш случайного 256-битного токена, срок, использованность, ожидаемые значения регистрации либо ссылка на существующего атлета |

Адрес восстановления уникален среди атлетов. Для сравнения адрес нормализуется
одинаково во всех потоках: пробелы по краям удаляются, регистр приводится к нижнему;
исходное написание сохраняется для отображения. Точки и суффиксы `+` не удаляются,
правила отдельных почтовых сервисов не имитируются. Ожидающая регистрация не является
аккаунтом и не резервирует дневник навсегда.

## Серверная сессия

Выбран случайный непрозрачный токен сессии в cookie `__Host-session`: `Secure`,
`HttpOnly`, `SameSite=Lax`, `Path=/`, без `Domain`. Сервер хранит хеш и проверяет
сессию по PostgreSQL при каждом запросе; локальная память процесса не является
источником действительности сессии. Redis и JWT в браузерном хранилище не требуются.
`Lax` допускает возврат верхнеуровневым переходом от OAuth-провайдера.

Технические значения первой версии: 30 суток без активности, абсолютный срок
90 суток от входа; cookie не живёт дольше абсолютного срока. Активность продлевает
только срок бездействия, а не абсолютную границу. Это выбранные параметры проекта
для длительной сессии, а не норматив OWASP или обещание работы провайдера.
При входе и подтверждении владения аккаунтом создаётся новый токен вместо прежнего
в этом браузере. Старый отзывается; параллельные ответы обычных запросов не выдают
его заново. CSRF-токен также обновляется. Истёкшая/отозванная сессия даёт `401`.

Изменения выполняются с CSRF-токеном, привязанным к серверной сессии, в отдельном
заголовке и с проверкой `Origin`. Для предварительного входа используется отдельная
краткоживущая браузерная попытка с таким же принципом защиты. Начало входа и
подключения — защищённые действия; OAuth callback вместо обычного CSRF-токена
проверяет собственные `state`, провайдера и браузерную привязку. CORS не разрешает
произвольный origin с credentials. Обычные GET не принимают команды изменения
плана, факта, пароля или способов входа. Календарное приведение перед чтением
сохраняется по T003; OAuth callback завершает вход только после проверки одноразовой
попытки, а подключение способа подтверждается отдельным защищённым POST.
Ответы с личными данными и секретами используют `Cache-Control: no-store`.

Выход отзывает текущую сессию в БД и очищает cookie. До подтверждения выхода клиент
не сообщает, что серверный доступ отозван. Интерфейс и память личных данных очищаются;
поведение неподтверждённого ввода описывается в T007. Запросы и сессии других устройств
не исчезают от обычного выхода в одном браузере. Восстановление пароля отзывает все
старые сессии. Команда изменения под общей блокировкой владельца повторно проверяет
действительность сессии/редакцию доступа: если отзыв уже подтверждён, ожидающая команда
не может затем записать данные. Если запись завершилась раньше отзыва, она остаётся
обычной подтверждённой записью.

Основания: [сессии NestJS](https://docs.nestjs.com/techniques/session),
[OWASP: сессии](https://cheatsheetseries.owasp.org/cheatsheets/Session_Management_Cheat_Sheet.html),
[OWASP: CSRF](https://cheatsheetseries.owasp.org/cheatsheets/Cross-Site_Request_Forgery_Prevention_Cheat_Sheet.html).

## Яндекс и ВКонтакте

Для обоих адаптеров выбран Authorization Code с PKCE S256. Nest создаёт случайные
`state` и verifier, сохраняет попытку на 10 минут и перенаправляет к выбранному
провайдеру. Redirect URI заранее зарегистрирован и не берётся из произвольного
параметра клиента. При возврате проверяются попытка, срок, назначение, браузер,
провайдер и точное совпадение `state`; попытка потребляется однократно. Обмен кода
и получение профиля выполняются сервером, вне транзакции дневника.

Идентификатор провайдера извлекается из проверенного сервером ответа профиля,
не из переданного SPA имени или почты. Если адаптер использует ID token, он проверяет
подпись, issuer, audience, срок и nonce по протоколу провайдера; непроверенный JWT
не служит доказательством входа. Токены провайдера не заменяют сессию приложения
и не передаются в SPA; после получения необходимых данных длительно не хранятся.

Яндекс поддерживает `state`, PKCE `S256` и обмен кода с verifier; профиль запрашивается
с правами на имя и почту. У VK ID используются актуальные code/PKCE, `state` и
`device_id` по протоколу VK ID, а не устаревшая интеграция старого VK OAuth.
Доступность кабинетов, redirect URI и нужных разрешений проверяется в E010 до
подключения; само наличие SDK не подтверждает внешние доступы владельца.

1. Уже подключённый `(provider, subject)` возвращает прежнего атлета, даже если
   провайдер теперь прислал другую почту. Имя и адрес восстановления молча не меняются.
2. Новый subject и незанятая переданная провайдером почта создают атлета и способ входа
   атомарно; дневник открыт без отдельной формы регистрации. Нет дополнительного
   подтверждения письмом в обычном потоке, как требует [auth](../../../../requirements/auth/index.md), R3.
3. Новый subject с уже занятой почтой не создаёт атлета и не открывает дневник.
   Предлагается прежний способ входа либо восстановление; далее — явное подключение.
4. Без переданной почты сохраняется только ожидающая попытка. Атлет вводит адрес и
   подтверждает его письмом; до этого дневника и сессии атлета нет. Занятый адрес
   переводит в тот же поток существующего аккаунта, а не прикрепляется автоматически.

После успешного обмена кода OAuth-попытка завершена. Если для регистрации ещё нужна
почта, проверенная личность провайдера переносится в отдельную ожидающую регистрацию
на 24 часа, привязанную к исходному браузеру. Это не продление жизни кода OAuth.
Подтверждение письма повторно проверяет срок этой записи и принадлежность subject;
при истечении требуется новый вход провайдером.

Основания: [Яндекс: code и PKCE](https://www.yandex.ru/dev/id/doc/ru/codes/code-url),
[Яндекс: профиль](https://yandex.ru/dev/id/doc/ru/user-information),
[официальный исходный код VK ID](https://github.com/VKCOM/vkid-web-sdk/blob/master/src/auth/auth.ts),
[OWASP: OAuth](https://cheatsheetseries.owasp.org/cheatsheets/OAuth2_Cheat_Sheet.html).
Портал VK ID не удалось открыть при исследовании; параметры сверены с первичным
источником SDK. Перед реализацией адаптера E010 сверяет актуальную спецификацию
в кабинете VK ID, не копируя стороннюю устаревшую стратегию.

## Явное подключение к существующему дневнику

Длительная сессия сама по себе не является свежим доказательством для подключения.
Атлет подтверждает существующий аккаунт паролем либо новым входом через уже
подключённого провайдера. Подтверждение действительно 5 минут для одной операции
подключения; восстановление по почте также позволяет получить доступ и затем
подтвердить действие установленным паролем.

После этого начинается новая OAuth-попытка с целью «подключение» и привязкой к
этому атлету. Одновременно подтверждается новый способ входа; почта нового
провайдера может отличаться. Отдельное подтверждение атлета показывает провайдера
и новый аккаунт, адрес восстановления остаётся прежним. В одной транзакции сервер
повторно проверяет существующий аккаунт, свежесть обоих доказательств и уникальность
нового subject, затем добавляет способ. Отмена и ошибка ничего не меняют.

Если subject уже подключён этому атлету, результат — тот же способ без дубликата.
Если другому — подключение отклоняется; переноса и объединения дневников нет.
Уникальные ограничения `(provider, subject)` и адреса восстановления проверяются
в БД, а не только предварительным поиском. Две конкурентные регистрации или
подключения завершаются максимум одним созданием; проигравшая попытка повторно
классифицируется без доступа к существующему дневнику по одному совпавшему адресу.

## Почта, пароль и восстановление

Регистрация по почте принимает имя, адрес и пароль в ожидающую запись. Пароль
хешируется Argon2id с индивидуальной солью; выбранная библиотека и стоимость
проверяются на сервере при реализации E009. Исходный пароль не сохраняется в
ожидании, журналах и письме. Подтверждение адреса действует 24 часа, только для
своего назначения и одной регистрации. Переход из письма показывает подтверждение;
изменение выполняет явный POST, чтобы предварительный просмотр почтовым клиентом
не создавал аккаунт. После проверки токена в одной транзакции создаются атлет и
пароль; если адрес уже занят, старый пароль не меняется, предлагается вход/восстановление.

Вход сравнивает пароль только с действующим хешем и создаёт новую сессию. Ошибка одинакова для
неизвестного адреса и неверного пароля; проверка неизвестного адреса выполняет
сопоставимую по стоимости фиктивную проверку хеша. Пароли и адреса не попадают
в тексты диагностических ошибок. Приложение принимает длинные пароли и менеджеры
паролей; конкретные ограничения полей определяются в E009 по выбранной библиотеке.

Восстановление всегда отвечает одинаково: «Если адрес зарегистрирован, отправлено
письмо». Токен действует 30 минут, хранится только его хеш, назначение и связь с
существующим атлетом. Владелец токена задаёт новый пароль, POST атомарно потребляет
токен, меняет/устанавливает пароль и отзывает все прежние сессии. Все токены
восстановления этого аккаунта также становятся недействительными. Уже подключённые
провайдеры и идентификатор атлета сохраняются; дневник не создаётся и не копируется.
После этого атлет входит обычным способом. Повтор использованного или истёкшего
токена пароль не меняет и доступа не даёт.

При восстановлении БД из копии все восстановленные хеши паролей удаляются из
активных записей способов входа до открытия маршрутов входа. Это постоянное
изменение БД, а не настройка интерфейса или временный флаг процесса. Для отсутствующего
хеша выполняется сопоставимая фиктивная проверка; пароль не создаёт сессию и
не подтверждает подключение способа входа. Установка нового пароля требует нового
письма восстановления на подтверждённую почту по обычному потоку выше; идентификатор
атлета, дневник и подключённые провайдеры сохраняются. Новый вход через провайдера
не активирует прежний пароль. Старые токены и сессии отзываются отдельно по
[процедуре E003](../../e003-release-design/design/release-and-recovery.md).

Письма отправляются после транзакции; неуспех доставки не откатывает чужие данные
и не создаёт дневник. Можно запросить новое письмо с новым токеном. Домен ссылок
задаётся конфигурацией, не входящим Host; страница подтверждения не содержит
сторонних ресурсов и использует `Referrer-Policy: no-referrer`. Токен немедленно
удаляется из адресной строки после чтения, маршруты и тела запросов с ним не
записываются в access/application logs. Разные назначения токенов невзаимозаменяемы.

Лимиты задаются отдельно для входа, запроса письма и обмена OAuth; учитываются IP
и хеш нормализованного адреса, с временным ограничением, а не вечной блокировкой
аккаунта по действиям постороннего. Счётчики можно хранить в PostgreSQL.
Неизвестная почта не вызывает реальную отправку. Повторная регистрация не служит
сбросом существующего пароля. Без доступа и к подключённому провайдеру, и к почте
автоматическое восстановление не обещается.

Основания: [OWASP: восстановление](https://cheatsheetseries.owasp.org/cheatsheets/Forgot_Password_Cheat_Sheet.html),
[OWASP: хранение пароля](https://cheatsheetseries.owasp.org/cheatsheets/Password_Storage_Cheat_Sheet.html),
[OWASP: аутентификация](https://cheatsheetseries.owasp.org/cheatsheets/Authentication_Cheat_Sheet.html).

## Ошибки и проверочные проходы

Публичные ошибки сообщают действие для атлета, код и непрозрачный идентификатор
операции. Диагностика содержит тип операции и итог, но не cookie, OAuth-код,
токены писем, пароли, почту, нотацию, факт или комментарий. Исключения БД и ответы
провайдера не возвращаются целиком в браузер. Секреты задаются в окружении сервера
вне git; тестовое окружение использует другие доступы и безопасную доставку писем.

| Исходная ситуация и действие | Проверяемый результат |
|---|---|
| Первый вход Яндексом с незанятой почтой | Один атлет и один способ; сессия открывает пустой дневник без формы регистрации |
| Повтор того же subject с изменившейся почтой | Тот же дневник; адрес восстановления прежний |
| Новый VK subject прислал почту существующего атлета | Дневник закрыт, дубликата нет; предложены прежний вход/восстановление |
| Провайдер не прислал почту | До письма только ожидающая попытка; подтверждение незанятого адреса создаёт одного атлета |
| Свежий вход прежним способом, затем явное подключение нового провайдера с другой почтой | Новый способ относится к прежнему атлету, адрес восстановления не изменён |
| Новый subject уже принадлежит другому атлету | Подключение отклонено, обе стороны без изменений |
| Два одновременных подтверждения одной почты/subject | Ограничения БД допускают одного атлета/одну связь; второй запрос не получает чужую сессию |
| Аккаунт создан Яндексом, запрос восстановления и новый пароль | Тот же атлет; провайдер сохранён, прежние сессии отозваны, токен повторно не действует |
| Подделаны state, цель login/link либо callback пришёл в другой браузер | До создания/подключения отказ; дневник закрыт |
| Чужой ID подхода, зала, истории, собственного веса или квитанции | Одинаковое «Не найдено», никаких чужих данных и изменений |
| Запрос изменения без CSRF или с посторонним Origin | Отказ до изменения; SameSite не является единственной проверкой |
| Сессия истекла во время ввода | `401`, факт не подтверждён; ввод не стирается, путь восстановления и повтора передаётся в T007 |
| Выход подтверждён, старая cookie повторно отправлена | Сессия отозвана в БД; отложенная команда после отзыва не сохраняется |
| Открыт калькулятор в браузере с живой сессией | Нет запроса сессии, чтения дневника и автоматического перехода |

## Проверка критериев T006

| Критерий | Где проверен |
|---|---|
| Два провайдера, почта, подтверждение, восстановление, длительная сессия и выход | Полные потоки, жизненный цикл и технические сроки |
| Совпадение почты не авторизует | Развилка нового subject; пример VK с занятым адресом |
| Один дневник после подключения/восстановления | Устойчивый атлет, уникальность и атомарные операции; конкурентные примеры |
| Владение во всех операциях | Таблица границ, вложенные ссылки, пакетные операции и производные результаты |
| Доверие, сессия и ошибки | PKCE/state, CSRF, ротация/отзыв, ограничения секретов и диагностик |
| Независимость калькулятора | Отдельная точка входа и последний проверочный пример |

Проверка проектная: таблицы сверены с [auth](../../../../requirements/auth/index.md), R1–R9,
и выбранным стеком. Проверка типов, одиночные и полные тесты приложения неприменимы,
поскольку кода и зависимостей по границам задачи нет. Для E009–E011 эти примеры задают
проверки интеграций, уникальности, изоляции, отзыва и повторов. Результат связан с PRD и реестром задач E001.
