# Локальная автоматическая проверка изменения

Инструкция относится к [E006-T001](./tasks/t001-automated-checks.md).
Проверка не развёртывает приложение и не получает полномочий выпуска.
Тестовое развёртывание T002 и восстановление после обновления T003 отложены;
успешная T001 не означает готовности всего E006 или E003/S01.

## Подготовка и запуск

Нужны Git, `tar`, Node.js 24.19.x или более новый 24.x, npm 11.x и запущенный
Docker Desktop/Engine с Compose. Для первоначальной установки нужны доступ
к реестру npm, загрузке Chromium Playwright и образу PostgreSQL.
Это загрузка локальных зависимостей, внешние сервисы приложения не используются.

Браузеры Playwright устанавливаются один раз в общий пользовательский кэш
(на Windows — `%LOCALAPPDATA%\ms-playwright`). Повторный запуск использует
готовую версию; загрузка нужна только при её отсутствии или обновлении Playwright.
Кэш не удаляется при очистке прогона. Сам npm-пакет Playwright остаётся зависимостью
проекта с версией из lockfile; глобальный npm-пакет не требуется.

Текущий Docker context должен обращаться к локальному Unix-сокету (`unix:///…`)
или Windows named pipe (`npipe:////./pipe/…`). TCP-подключения, включая loopback,
и удалённые context не поддерживаются. Runner проверяет endpoint и фиксирует
его для Compose и тестов; родительские `DOCKER_HOST` и `DOCKER_CONTEXT`
не передаются. Проверить текущую настройку можно через `docker context show`
и `docker context inspect`.

Из корня репозитория:

```powershell
npm run check
npm run check -- --ref HEAD
```

Без `--ref` выбирается `HEAD`. Можно указать другой commit, tag или git tree:

```powershell
npm run check -- --ref <commit-or-tree>
```

Угловые скобки обозначают подставляемый идентификатор. Проверяемая версия
получается через `git archive`; `.env`, `node_modules`, `dist` и другие локальные
неотслеживаемые файлы не переносятся. Изменения рабочего каталога и индекса
не входят в проверку до создания соответствующего commit или tree.
Успех `HEAD` не подтверждает ещё не включённый в него новый код.
Команда не выполняет staging или commit за разработчика.

До извлечения runner отклоняет дерево с отслеживаемыми `node_modules`, `dist`,
`.git` или `.env*` в корне; исключение — `.env.example`. Символические ссылки
и submodules в любой части дерева также запрещены. Такая версия получает
неуспех этапа `snapshot`: уберите локальные артефакты и секреты из проверяемых
исходников, не переносите зависимости или сборку в git.

Не запускайте одновременно несколько полных проверок: существующие тесты
оболочки используют фиксированные локальные порты 3017, 3018 и 3020.
Отдельная случайная публикация порта PostgreSQL не устраняет это ограничение.

## Обязательные этапы

Этап `snapshot` разрешает выбранный ref в идентификаторы объекта и дерева git,
затем извлекает исходники во временный каталог `.scratch/checks-*`.
Последующие этапы выполняются в этой копии:

1. Установку зависимостей через `npm ci` по lockfile проверяемой версии.
2. Проверку Chromium в общем кэше и установку отсутствующей версии через Playwright из зависимостей проекта.
3. Подготовку отдельной синтетической PostgreSQL в собственном Compose-проекте.
4. Генерацию Prisma Client через `npm run db:generate`.
5. Проверку форматирования через `npm run format:check`.
6. Проверку типов через `npm run typecheck`.
7. Подготовку API и SPA через `npm run build`.
8. Полный набор через `npm test`.
9. Очистку созданных проверкой ресурсов.

Это те же команды приложения, что используются при
[локальном запуске и работе с хранилищем](../../../../README.md).
`build` дополнительно повторяет генерацию Prisma Client и проверку типов;
отдельные этапы позволяют различить их результат в общем прогоне.
Проверки миграций входят в существующие интеграционные тесты: чистая схема,
повтор, обновление прежней схемы с сохранением строки и контролируемый отказ.
Сборка выполняется до тестов, потому что HTTP- и серверные проверки используют `dist`.

## Изоляция и очистка

Проверочная PostgreSQL слушает только loopback на автоматически назначенном порту.
Проект Compose и данные принадлежат конкретному прогону; рабочая БД
`kachok-local`, её постоянный том и `.env` разработчика не используются.
Тесты получают адрес синтетического кластера и создают свои отдельные случайные БД.
Проверка журналов PostgreSQL обращается к тому же проверочному Compose-проекту.

После успеха или ошибки runner удаляет свой Compose-проект с его данными
и временную копию исходников. Это удаление одноразового проверочного хранилища,
а не способ исправления миграции приложения. Правила безопасных миграций
и диагностики остаются в [основной инструкции](../../../../README.md#локальное-хранилище).

Если очистка Compose не удалась, runner сохраняет временную копию для повторной
очистки и завершает проверку неуспехом. После восстановления Docker найдите
созданный прогоном проект `kachok-checks-*` и его `compose.checks.yaml` внутри
`.scratch/checks-*/source`. Перед ручной командой сверьте имя проекта; рабочий
`kachok-local` удалять нельзя:

```powershell
docker compose -p <project-name> -f <path-to-compose.checks.yaml> down --volumes --remove-orphans
```

При SIGINT/Ctrl+C или SIGTERM runner прерывает выполняемую команду и переходит
к очистке. При принудительном завершении без обработки сигнала автоматическая
очистка не гарантируется; проверочные ресурсы удаляются тем же способом.

Рабочие секреты, личные данные и полномочия развёртывания не нужны.
Не передавайте их проверке. Почта при добавлении почтовых сценариев должна
перехватываться локальным Mailpit; внешний SMTP не допускается.

## Результат и повтор после ошибки

Runner выводит JSON-события по одному на строку в stdout; обычный вывод
инструментов поступает в stderr. Для stdout без служебного заголовка npm используйте
`npm --silent run check -- --ref HEAD`. У события этапа есть поля `stage` и `status`
со значениями `started`, `passed` или `failed`. Порядок этапов:
`snapshot`, `install`, `browser`, `database`, `generate`, `format`, `typecheck`,
`build`, `test`, затем `cleanup`.

Событие `source` после подготовки копии содержит `source` — идентификатор
выбранного объекта git и `tree` — идентификатор дерева исходников.
Итоговое событие `summary` содержит `status`, `source`, `tree` и при неуспехе
`failedStage`. До разрешения ref идентификаторы могут быть `null`;
неверные аргументы дают `CHECK_CONFIGURATION_FAILED`.
Отказ команды дополнительно обозначается `CHECK_COMMAND_FAILED` с её `exitCode`,
отказ этапа — `CHECK_STAGE_FAILED`. Исходные тексты исключений runner не публикует.

Установка, генерация, типы, сборка и тесты имеют
отдельные результаты; ошибка обязательного этапа останавливает дальнейшую
проверку и даёт ненулевой код завершения. Ошибка очистки также не должна
маскироваться успешным итогом.

Проверяйте итоговый код процесса, а не только сообщение об успешной сборке.
Для воспроизведения ошибки повторите ту же команду с тем же `--ref`.
Если Docker недоступен, сначала запустите его. Если не устанавливаются
зависимости или Chromium, восстановите доступ к загрузке. Ошибки типов,
сборки или тестов исправляются в исходниках; для проверки исправления
выберите новое состояние git.

Контроль неуспеха выполняется на отдельной проверочной версии с намеренной
ошибкой типов или падающим тестом. Она должна дать неуспех соответствующего
этапа и процесса. После исправления новая версия должна пройти весь набор.
Не вносите контрольную ошибку в рабочие файлы другого разработчика.
