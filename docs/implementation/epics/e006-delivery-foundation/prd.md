# E006. Автоматические проверки и тестовое развёртывание

## 1. Результат

Каждое изменение приложения получает воспроизводимую автоматическую проверку,
а прошедшая проверку сборка может быть развёрнута в тестовом окружении по инструкции.
Разработчик определяет работающую сборку и находит причину ошибки по диагностике.

## 2. Границы

**Входит:** автоматическая установка зависимостей и подготовка приложения,
обязательные проверки, безопасная конфигурация тестового окружения, развёртывание,
проверка доступности и миграций, диагностика ошибок и инструкция разработчика.

**Не входит:** функциональная приёмка ещё не реализованных сценариев, публичный выпуск,
проверка резервного восстановления всей первой версии и организация постоянной
эксплуатации. Эти результаты относятся к S11. Не вводятся сторонние сервисы,
инструменты или платные возможности без согласованных решений S01.

## 3. Входные решения и зависимости

Необходимы **согласованные с пользователем решения S01** о стеке, инструментах проверок,
размещении, окружениях, диагностике, передаче секретов и восстановлении после ошибки.
До этого согласования проект не создаётся и зависимости не устанавливаются.
Здесь не выбираются сервис автоматизации, хостинг или инструменты наблюдения.

Входы: завершённый **E003**, локальный запуск [E004](../e004-project-foundation/README.md) и подключение
хранилища с миграциями [E005](../e005-storage-foundation/README.md). Подготовка
автоматических проверок возможна после E004; завершение эпика требует обоих результатов.
Перед разбиением на задачи PRD получает ссылки на согласованные решения S01.

## 4. Сценарии

### Проверка изменения

1. Автоматический запуск получает исходники определённого состояния git.
2. Устанавливает зависимости воспроизводимым способом из конфигурации проекта.
3. Выполняет обязательные проверки, принятые в S01, и готовит приложение.
4. Показывает отдельный результат каждой обязательной проверки.
5. При ошибке изменение не получает успешный итог; ошибку можно воспроизвести локально.

### Развёртывание проверенной сборки

1. Выбирается сборка, прошедшая обязательные проверки.
2. Тестовое окружение получает собственную конфигурацию и секреты отдельно от исходников.
3. Миграции выполняются в порядке, определённом S01 и E005.
4. Приложение запускается; проверяются оболочка, прямые ссылки и подключение хранилища.
5. Фиксируется идентификатор работающей сборки; повторное развёртывание воспроизводимо.

Момент запуска развёртывания — автоматически или вручную — определяется согласованной
схемой S01. Успешная сборка сама по себе не означает успешного развёртывания.

### Неуспешное развёртывание

Разработчик определяет неуспешный этап, находит связанную диагностику и действует по
инструкции восстановления из S01. Ошибка миграции не скрывается перезапуском и не
исправляется очищением хранилища. Доступность предыдущей версии и совместимость
схемы проверяются способом, предусмотренным согласованной стратегией обновления.

## 5. Проект реализации и интерфейсы

| Часть | Ответственность | Контракт результата |
|---|---|---|
| Автоматические проверки | Сборка и проверки того же кода, что доступен локально | Явный успешный или неуспешный итог и причина |
| Подготовленное приложение | Результат проверенного состояния исходников | Прослеживается до состояния git |
| Тестовое окружение | Изолированная конфигурация и хранилище | Не использует личные секреты или реальные тренировочные данные |
| Развёртывание | Применение конфигурации, миграций и запуск | Известна работающая сборка и результат проверки доступности |
| Диагностика | Ошибки запуска, запросов и зависимостей | Можно найти причину без раскрытия секретов и личного содержимого |

Установка зависимостей использует зафиксированную проектом конфигурацию выбранного
инструмента. Проверки не зависят от файлов и секретов, существующих только на машине автора.
Проверки калькулятора позднее добавляются без требования подключения к дневнику.

Автоматическая проверка отделена от доступа к тестовому окружению: проверка обычного
изменения не должна получать полномочия на развёртывание, если они ей не требуются.
Конкретный способ передачи секретов определяется S01, а инструкция описывает его
без включения реальных значений в git или диагностические сообщения.

## 6. Диагностические данные и документация

Минимальный диагностический результат позволяет сопоставить ошибку с этапом запуска
или обработки, сборкой и недоступной зависимостью. Стек выбранного инструмента,
сообщения исключений и параметры подключения не показываются атлету.

Инструкция разработчика содержит предварительные условия, команды локальной проверки,
способ запуска автоматической проверки, параметры тестового окружения, команды
развёртывания и миграций, проверку доступности и действия после неуспешного обновления.
Она ссылается на инструкции E004–E005 и не создаёт расходящихся копий одних команд.

## 7. Критерии приёмки

- [ ] Выбранные инструменты и окружение соответствуют согласованным с пользователем
  решениям S01; ссылки на эти решения добавлены до начала реализации.
- [ ] Автоматическая проверка воспроизводимо устанавливает зависимости, выполняет
  обязательные проверки и готовит приложение из чистого окружения.
- [ ] Контрольное ошибочное изменение даёт неуспешный итог; исправленное — успешный.
- [ ] Документированными локальными командами воспроизводится тот же обязательный
  набор проверок; различия окружений явно описаны.
- [ ] Тестовая сборка прослеживается до состояния git и развёртывается по инструкции;
  идентификатор работающей сборки доступен разработчику.
- [ ] После развёртывания работают оболочка, прямые ссылки контекстов и подключение
  хранилища; повторное развёртывание не стирает проверочные данные.
- [ ] При недоступном хранилище, ошибке миграции и ошибке запуска видна причина этапа,
  а не ложный успешный итог развёртывания.
- [ ] Согласованный порядок действий после неуспешного развёртывания проверен
  на тестовом окружении и описан в инструкции.
- [ ] Реальные секреты отсутствуют в git, клиентской сборке и диагностике; для проверки
  изменений не используются полномочия развёртывания без необходимости.
- [ ] Тестовое окружение не содержит реальные личные данные; инструкции не требуют
  неописанных ручных настроек на машине автора.

## 8. Проверки и риски

Проверяются успешный путь, намеренно проваленная проверка и неуспешное обновление
на тестовых данных. Полноценное восстановление резервной копии продукта проверяется
в S11; наличие инструкции на этом шаге не считается выполнением той приёмки.

| Риск | Мера |
|---|---|
| Проверки локально и автоматически расходятся | Общий обязательный набор и воспроизводимые команды |
| Сборка успешна, приложение недоступно | Отдельная проверка запуска, прямых ссылок и хранилища |
| Окружение зависит от секретов автора | Отдельная конфигурация и описанный способ передачи секретов |
| Ошибка обновления исправляется уничтожением данных | Проверенный порядок восстановления без очистки хранилища |
| Диагностика раскрывает личные данные | Ограниченный состав диагностических сведений без содержимого записей |

## Принятые технические решения E001

Сборки React SPA/Vite и NestJS проверяются отдельно и размещаются на одном сервере Docker Compose с
PostgreSQL. Проверки реализации включают typecheck, предметные/интеграционные тесты и сборку.
Готовые Prisma Migrate проверяются на отдельной БД до применения; /api не обслуживается
SPA-заглушкой. Окружения разделяют данные, секреты и доставку почты. Копии исключены из объёма E001;
действующий проект задан [T004 E003](../e003-release-design/design/release-and-recovery.md),
штатная настройка и проверка восстановления выполняются в E029.

Основание: [результат E001](../e001-technical-design/design/technology-stack.md),
[ADR-0020](../../../architecture/adr/ADR-0020-javascript-modular-monolith.md),
[ADR-0021](../../../architecture/adr/ADR-0021-durable-drafts-and-operation-receipts.md).

## Условия E003: проверки, test и диагностика

[Проект окружений](../e003-release-design/design/environments-and-access.md) требует
синтетическую test-БД, отдельные сети/тома/секреты и перехват всей тестовой почты.
Обычная проверка изменения не получает рабочие credentials и полномочия выпуска.
Подключаемость внешних кабинетов подтверждается отдельно; имитации её не доказывают.

[Матрица проверок](../e003-release-design/design/acceptance-matrix.md) определяет группы
будущих тестов; каждый эпик добавляет проверки до своей приёмки. Проверенная сборка
связана с состоянием git и применяется по [процедуре выпуска](../e003-release-design/design/release-and-recovery.md):
отдельные результаты сборки, миграции, запуска и проверки доступности, остановка
при неудаче. При обычном выпуске поколение восстановления не меняется.

[Проект диагностики](../e003-release-design/design/diagnostics-and-handoff.md) задаёт
разрешённые поля, безопасные маршруты и контрольные сбои G01–G06/G08. До приёмки
проверяются недоступная БД, отказ миграции, потеря ответа, сессия/конфликт, отказы
почты/OAuth и отсутствие контрольных секретных строк во всех журналах. Журналы
доступны оператору, ротируются не дольше семи суток; предел диска определяется
по серверу и проверяется без заполнения рабочего диска. Квитанции БД не очищаются
по сроку диагностического журнала. Подробные команды создаются здесь и в E004/E005;
проект E003 сам по себе не является работающей автоматизацией.
