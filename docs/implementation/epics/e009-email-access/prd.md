# E009. Личный дневник и вход по почте

## Результат

Атлет без аккаунтов внешних провайдеров создаёт личный дневник через почту с паролем.
Потеря пароля или недоступность провайдера не отрезает доступ: подтверждённое действие
из письма позволяет установить пароль и открыть тот же дневник.
Это запасной способ входа; основными остаются провайдеры из E010.

## Границы

**Входит:** регистрация по почте, подтверждение владения адресом до создания дневника,
вход с паролем, восстановление доступа, установка пароля к существующему дневнику,
обработка повторной регистрации и неуспешных подтверждений.

**Не входит:** подключение внешних провайдеров (E010), окончательная приёмка сессий
и изоляции всех личных данных (E011), объединение дневников, роли и администрирование.
Удаление аккаунта остаётся отложенным по [бэклогу](../../../backlog.md), «Удаление аккаунта»;
его триггер перед публичным доступом проверяется при проектировании выпуска.

## Сценарии

1. Атлет явно выбирает ведение дневника и запасной способ входа по почте.
   Вводит имя, адрес и пароль. До подтверждения владения адресом дневник не создаётся.
2. Подтверждение из письма завершает регистрацию и открывает пустой личный дневник.
   Повторное завершение того же действия не создаёт второй дневник.
3. Уже зарегистрированный атлет входит по почте с паролем в прежний дневник.
4. Повторная регистрация существующего адреса предлагает вход или восстановление,
   не создаёт новый дневник и не заменяет существующий пароль.
5. При восстановлении атлет получает письмо, подтверждает владение адресом и задаёт
   пароль. Открывается тот же дневник с прежними данными и подключёнными провайдерами.
6. Восстановление к дневнику, созданному через провайдера, устанавливает первый пароль
   к этому аккаунту. Совпадение введённого адреса само по себе доступ не даёт.
7. Отмена, неуспешное или непригодное подтверждение не меняют пароль и данные аккаунта.
   Без доступа к почте и подключённым способам автоматическое восстановление не обещается.

## Проект реализации

### Данные и ответственность

| Данные | Назначение и ограничение |
|---|---|
| Атлет | Устойчивый идентификатор владельца, имя, обязательная почта, дата регистрации |
| Способ входа по почте | Связь пароля с существующим атлетом; отсутствие пароля допустимо для входа через провайдера |
| Незавершённая регистрация | Временные данные до подтверждения адреса; это ещё не созданный дневник |
| Подтверждение владения | Назначение действия, адрес и связанный запрос; результат проверяется на стороне доступа |
| Результат входа | Идентичность атлета для механизма сессии E011; личные данные не передаются калькулятору |

Операции регистрации, входа и восстановления принадлежат границе доступа.
Создание атлета и его дневника должно иметь единый результат: частичный сбой не оставляет
второй аккаунт или дневник без владельца. Уникальность существующего адреса проверяется
при завершении регистрации, включая одновременные запросы.

Пароль и подтверждение не хранятся в открытом виде в диагностике, документации или git.
Конкретные способы защиты пароля, срок и однократность подтверждений, обработка повторных
писем и ограничения попыток уточняются по согласованным решениям S01 перед задачами.
Поставщик отправки почты определяется в E003; формат команд и технология сессии
заданы результатами E001 ниже.

### Операции

Граница предоставляет начало регистрации, завершение подтверждения, вход по паролю,
начало восстановления и подтверждённую установку пароля. У каждой операции различаются
ожидание, успех и неуспех; запрос письма не считается подтверждением владения.
Подключаемый в этом эпике механизм доставки возвращает результат отправки, а подтверждение проверяет
сама граница доступа. Сбой доставки не создаёт аккаунт и не меняет пароль.

После входа открывается пустой дневник с будущим действием создания первого цикла.
Создание цикла в этот эпик не входит. Все сообщения и формы — на русском языке.

## Зависимости

- Результаты E004–E006 из [реестра](../README.md): окружения, хранение, конфигурация и проверки.
- Согласованные с владельцем решения S01 об аутентификации, почте и хранении секретов.
- E010 использует подтверждение почты и восстановление для провайдера без адреса
  и подключения нового способа входа; E011 принимает общие правила сессий и защиты данных.

## Критерии приёмки

- [ ] A1. Новый адрес с обязательным именем создаёт ровно один дневник только после
  подтверждения владения почтой; повтор и одновременное завершение не создают дубликаты.
- [ ] A2. Вход с правильным паролем открывает прежний дневник; неуспешный вход его не открывает.
- [ ] A3. Повторная регистрация существующего адреса не изменяет пароль, способы входа
  и данные; доступен путь входа или восстановления.
- [ ] A4. Подтверждённое восстановление заменяет пароль того же аккаунта и сохраняет данные.
  Для аккаунта провайдера устанавливается пароль без потери подключённых провайдеров.
- [ ] A5. Введённый адрес, совпавшее имя, запрос письма или неуспешное подтверждение
  не дают доступа и не изменяют аккаунт; сбой доставки не создаёт дневник.
- [ ] A6. Сценарии доступны с мобильного экрана; формы и состояния русские;
  почта с паролем остаётся запасным вариантом, а не обязательной формой перед провайдером.

## Проверки и риски

Проверяются новый адрес, существующий адрес с паролем и без него, отменённое подтверждение,
ошибка доставки, повтор подтверждения и параллельное завершение регистрации.
Проверка восстановления должна сверять идентификатор дневника и сохранность его записей,
а не только возможность выполнить вход после смены пароля.

Главный риск — трактовать совпадение адреса как доказательство владения.
Операции изменения доступа завершаются только после предусмотренного подтверждения.
Второй риск — зависимость от почты: до приёмки нужен проверяемый канал доставки в тестовом
окружении и согласованное поведение при его недоступности.

## Принятые технические решения E001

Почта подтверждается до создания атлета; пароль хранится Argon2id-хешем, токены писем — хешами с
назначением и однократным потреблением. Восстановление меняет пароль того же атлета, сохраняет
провайдеров и отзывает все старые сессии, без нового дневника. Повторная регистрация занятого адреса
не меняет пароль. Сессия серверная в PostgreSQL; cookie HttpOnly/Secure, изменения защищены CSRF и
Origin.
