# Ограничения мобильных схем и условия проверки

Вход для проектирования [E002](../prd.md) и частичный результат согласования с
[E003](../../e003-release-design/prd.md). Перечень браузеров и условия ниже приняты
как проектная граница по поручению владельца самостоятельно разрешать технические
вопросы. Они не определяют аудиторию, бюджет или готовность выпуска E003.

## Технические границы

| Решение E001 | Требование к экрану E002 |
|---|---|
| React SPA/Vite, NestJS, Prisma, одна PostgreSQL | Статическая оболочка загружает данные дневника с сервера; только сервер подтверждает сохранённый план и факт |
| Ant Design и Tailwind CSS | Готовые поля, кнопки и сообщения оформляются общей темой; карточки и вертикальные списки не требуют широкой таблицы |
| Отдельная точка входа калькулятора | Калькулятор не проверяет сессию, не запрашивает дневник и не хранит введённое; переход в дневник всегда явный |
| Ручной ввод без МПВ | Никакая пустая подсказка не закрывает доступ к плану; неизвестный МПВ не представляется нулём |
| Дата сервера, Europe/Moscow | Запрет изменения плана объясняется календарём дневника; часы телефона не разрешают запрещённую правку |
| Отдельная фиксация разминки и основной части | Отметка разминки не блокирует основной план; первый факт основной части фиксирует её целиком |
| Фиксация календарём | Незаполненные веса копии после фиксации не дописываются из истории или факта задним числом |
| Постоянные квитанции операций | Повтор после потерянного ответа относится к прежней команде; повторное касание не создаёт дополнительный подход |
| Зашифрованный черновик на устройстве | Только завершённая локальная запись даёт надпись «Черновик на устройстве»; факт появляется после подтверждения сервера |
| Проверка владельца | После истечения сессии личные поля скрываются; продолжить прежний ввод может тот же атлет после входа |

Основания: [стек](../../e001-technical-design/design/technology-stack.md),
[модель](../../e001-technical-design/design/manual-plan-and-fact.md),
[календарь](../../e001-technical-design/design/calendar-and-interruption.md),
[протокол сохранности](../../e001-technical-design/design/input-preservation.md).

## Почему NestJS и статический React подходят

Выбор уже закреплён в [ADR-0020](../../../../architecture/adr/ADR-0020-javascript-modular-monolith.md).
Личный дневник не требует поисковой индексации или серверного рендеринга, а калькулятор
должен считать в браузере. Поэтому React SPA отдаётся статикой, а NestJS остаётся
единственным прикладным сервером. Prisma применяется с PostgreSQL, как поручил владелец.

| Вариант | Польза | Цена и решение |
|---|---|---|
| NestJS + React SPA | Модульные границы, общие соглашения валидации и доступа; отдельная статическая сборка интерфейса | Две сборки и явные контракты API, загрузки и ошибок; приемлемо для связанных операций дневника |
| Next.js с SSR + NestJS | Серверное получение данных и рендеринг | Дополнительный серверный слой при отсутствии потребности SSR; не выбран |
| Next.js со статическим экспортом | Можно выпускать статические страницы | Модель маршрутов и ограничения экспорта не дают преимущества для выбранного разделения SPA/API |
| React + Express/Fastify без NestJS | Меньше соглашений и служебного кода в начале | Границы модулей, владение, валидацию и ошибки пришлось бы согласовывать самостоятельно; не выбран |

NestJS не рассчитывает предметные правила сам, а Prisma не устраняет конкуренцию.
Общие транзакции, проверка редакции и повтор по квитанции остаются обязанностью
прикладного кода E001. Выбор готовой библиотеки также не доказывает удобство на телефоне:
клавиатура, фокус и касания требуют отдельной приёмки.

## Браузеры и размеры

Основная матрица первой версии — Safari на iPhone/iOS и Chrome на Android в обычном
режиме вкладки. Для каждой пары проверяются стабильная версия на момент фиксации
приёмки и непосредственно предыдущая доступная версия. Точные версии ОС, браузера,
устройство и сборка приложения записываются в протоколе фактического прогона.
Этот выбор задаёт объём проверки, а не обещает совместимость ещё не выбранных
версий библиотек. В E004 минимумы Ant Design/Tailwind сверяются с матрицей до установки
зависимостей; несовместимый выбор возвращается в проект, а не сужает матрицу молча.

Схемы рассматриваются при ширине 320, 360 и 390 CSS-пикселей в портретной ориентации.
Для тесного состояния используется видимая область высотой 280 CSS-пикселей после
появления клавиатуры. Это модель компоновки, а не утверждение о высоте клавиатуры
конкретного устройства. На реальном устройстве проверяется фактическая видимая
область, включая панели браузера и безопасные отступы. Альбомная ориентация и масштаб
текста 200% не должны скрывать поля и действия или требовать смены ориентации.

При вводе нотации нужна доступность `/`, `*`, `-` и десятичного разделителя;
цифровая клавиатура сама по себе не считается достаточной. Для отдельного веса
клавиатура десятичная, для повторений — целочисленная. Если нужного символа нет,
предусматривается переключение клавиатуры без потери текста. Порядок полей и
переходов фокуса проверяется касаниями и внешней клавиатурой.

## Матрица документального прохода и будущей приёмки

| Проверка | Наблюдаемый результат на схемах и в будущем интерфейсе |
|---|---|
| Первый ручной план без истории и МПВ | От пустого дневника можно создать цикл, выбрать упражнение и заполнить план; нет обязательного числового МПВ |
| Длинная неделя | Три тренировки по восемь упражнений с шестью подходами доступны вертикальной прокруткой; название в несколько строк не перекрывает вес и действие |
| Нотация с клавиатурой | Текущий ввод и разбор доступны без закрытия редактора; исходная строка при ошибке сохраняется, неоднозначность не принимается молча |
| Копия без весов | «Не заполнено» отличается от нуля и факта; доступность дополнения связана с фиксацией плана |
| Основной исход подхода | Одно касание создаёт и отправляет команду без второй кнопки; следующее упражнение остаётся видимым в компактной строке, правка остаётся на месте |
| План, факт и черновик | Различаются подписью и оформлением, а не только цветом; ответ сервера не стирает более свежую правку |
| История | План читается отдельно от факта и действительной даты; фиксация плана не скрывает разрешённое исправление факта |
| Потеря связи и ответа | Введённое видно до истечения сессии; неизвестный результат не изображается отказом или успехом; повтор не создаёт дубль |
| Истечение сессии и смена аккаунта | Личные поля скрыты; после входа тем же атлетом предлагается продолжить; другой аккаунт не получает прежний черновик |
| Локальное хранилище недоступно | Нет ложной надписи о сохранности; ввод остаётся в памяти, объяснён риск закрытия вкладки и доступно повторение локальной записи |
| Калькулятор с несколькими карточками | Три попытки, общий выбор формулы и полный рейтинг доступны на одной странице; равные итоги не получают выдуманного преимущества |
| Калькулятор с открытой сессией дневника | Нет запросов сессии/API и подстановки данных дневника; перезагрузка очищает сравнение |
| Фокус и чтение | Видимый фокус, подписи ошибок рядом с полями, логичный порядок чтения; состояние различимо без цвета |

На проектном этапе проверяется наличие соответствующих экранов, переходов и
состояний в документах T001–T006. Фактические касания, поведение экранной клавиатуры,
чтение вспомогательными средствами и обработка сбоев в работающем браузере проверяются
после реализации в S02–S11. Эмуляция размера не заменяет реальные Safari и Chrome.
Данный документ не является протоколом успешного браузерного прогона.

## Передача и границы приёмки

E002 использует эту матрицу для общей проверки A1–A8 и связывает каждую строку
с конкретными схемами T001–T006. E003 получает браузеры и условия как вход для
[матрицы проверок](../../e003-release-design/tasks/t003-acceptance-matrix.md),
не дожидаясь завершения своего эпика. E004 получает ограничения компонентов и
версий; E028 получает воспроизводимые ручные сценарии и необходимость записать
реальные версии и результат. Аудитория, внешние аккаунты, бюджет и эксплуатационные
гарантии здесь не предполагаются и остаются предметом E003.
