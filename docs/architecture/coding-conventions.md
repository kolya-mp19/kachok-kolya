# Общие соглашения о коде

Эти правила и руководства по слоям обязательны для нового и изменяемого кода.
Они полностью находятся в репозитории: доступ к другим проектам или определённому
компьютеру не требуется.

## Что читать

| Задача | Руководство |
|---|---|
| Любые изменения TypeScript | Этот документ |
| API, серверные сценарии, доступ к БД | [Бэкенд: NestJS и Prisma](./backend-conventions.md) |
| Экран, компонент, форма, хук, браузерное хранение | [Фронтенд: React](./frontend-conventions.md) |
| Изменение контракта API | Оба руководства |

Примеры показывают форму кода. Условные модели БД, компоненты и зависимости в примерах
не считаются реализованными. Пример не разрешает добавлять новую функцию продукта,
зависимость или инфраструктуру. Бизнес-правила определяются спеками, ограничения — ADR.
При применении примера необходимо реализовать его зависимости и проверить сценарий.

## Читаемость сценария

По основному методу видно, что происходит и в каком порядке. Подробности запроса,
разбора входа или сериализации не должны скрывать этот порядок. Читателю не следует
восстанавливать сценарий из нескольких уровней изменяемых замыканий и callback.

Неудачная форма:

```ts
const save = async (x: unknown) => {
  if (!x || typeof x !== 'object') throw new Error('INVALID_INPUT');
  try { const r = await write(x); return { ok: true, result: r }; }
  catch { return { ok: false }; }
};
```

Предпочтительная форма с условными зависимостями:

```ts
async function saveOperation(input: unknown): Promise<OperationConfirmation> {
  const command = parseOperationCommand(input);
  const result = await executeOperation(command);

  return mapOperationConfirmation(result);
}
```

Вторая форма требует реализации разбора, выполнения и преобразования с явными контрактами.
Извлекать метод следует ради понятной обязанности, а не ради ограничения числа строк.
Простая функция не требует класса.

## Имена, файлы и зависимости

- Имена кода — английские, пояснения — русские. Использовать термины своего контекста:
  `athlete` в дневнике, `participant` в калькуляторе.
- Предпочитать `operationReceipt`, `draftRevision`, `athleteId` вместо `r`, `v`, `data2`.
  `tx` допустим для транзакции. В callback называть сущность:
  `exercises.map((exercise) => exercise.id)`.
- Булевы значения: `isSaving`, `hasPendingOperation`, `canEdit`. Методы — действия:
  `findById`, `saveDraft`, `verifyAccess`.
- Один основной сервис, репозиторий, контроллер или React-компонент — один файл.
  Маленькие приватные типы и функции оставлять рядом, пока они обслуживают этот файл.
- Код сначала принадлежит своей функции продукта. В общий каталог он переходит
  при реальном совместном использовании, а не из-за абстрактной возможности повторения.
- Не добавлять `index.ts` и цепочки переэкспортов автоматически; избегать циклов импортов.
- Алиас должен одинаково разрешаться при разработке, сборке, запуске и тестировании.
  До его настройки использовать относительные импорты. На API сохранять расширения
  `.js`, требуемые текущей конфигурацией NodeNext.
- Зависимости объявлять явно. Не скрывать их в глобальном состоянии, service locator
  или чтении окружения внутри предметной функции.

## Типы и контракты

У экспортируемых функций и публичных методов классов явно указывать результат,
включая `Promise<...>`. Для React-компонентов и хуков есть уточнения
в [руководстве фронтенда](./frontend-conventions.md).

Связанные параметры описывать именованным типом:

```ts
type FindExercisesParams = {
  athleteId: string;
  search?: string;
  skip: number;
  take: number;
};

type Page<T> = {
  items: T[];
  totalCount: number;
};
```

- `type` — обычный выбор для данных и объединений; `interface` подходит для реализуемого
  контракта. Префикс `I` не требуется. Не создавать оба вида для одной структуры.
- Не выводить публичный контракт через цепочки `ReturnType` и `Parameters` внутренней
  реализации. Он должен читаться самостоятельно.
- Для непроверенного входа и ошибок использовать `unknown`. Тип TypeScript и `as`
  не проверяют данные во время выполнения.
- Не применять `any`, `as unknown as ...`, необоснованный `!` или отключение проверок.
  При реальном ограничении библиотеки локализовать приведение, проверить данные
  и объяснить, почему проверка достаточна. `as const` допустим для литеральных значений.
- Не использовать `Partial<Entity>` как вход изменения: перечислять разрешённые поля,
  чтобы идентификатор, владелец и служебные поля не стали изменяемыми случайно.
- Задавать смысл `null` и `undefined`: например, `null` — объект не найден,
  `undefined` — необязательный параметр не передан.

Состояния с разными данными описывать объединением:

```ts
type LoadState<T> =
  | { status: 'loading' }
  | { status: 'ready'; data: T }
  | { status: 'failed'; message: string };
```

Так данные нельзя прочитать до успешной загрузки. Для простого локального переключателя
достаточно boolean; объединение не нужно добавлять ради единообразия.

## Управляющий поток и ошибки

- У `if`, циклов, `try` и `catch` — многострочные блоки с фигурными скобками.
  Несколько действий в одной строке не размещать.
- Сначала проверять предусловия и выходить при отказе. Основной сценарий не прятать
  под несколькими вложенными `else`.
- Длинное условие разделять на проверки или предикаты с предметными именами.
  Вложенные тернарные выражения не использовать.
- Независимые операции можно объединять в `Promise.all`, если частичное выполнение
  допустимо. Зависимые записи выполнять последовательно.
- Перед асинхронной операцией внутри `try` нужен `await`, если её отказ должен попасть
  в этот `catch`. В простом возвращающем методе допустим `return promise`.
- Не поглощать ошибку пустым `catch`, безусловным успехом или пустым списком.
  Ожидаемое подавление требует объяснения и корректного состояния отказа у потребителя.
- Перехватывать там, где можно восстановиться, добавить полезный контекст или перевести
  ошибку в контракт слоя. Повторно логировать один отказ в каждом слое не нужно.

## Комментарии и JSDoc

Код необходимо комментировать там, где причина поведения не следует из его структуры.
Обязательно объяснять неочевидные ограничения, защитные проверки, исключения из обычного
сценария, порядок операций при гонках и намеренное подавление ошибок. Если проверка
вызвана отдельным бизнес-правилом или ADR, указывать это основание.

Не требуется комментарий к каждому методу или `if`. Очевидная проверка формата или
пустого обязательного поля не нуждается в пересказе, если её назначение уже ясно.
Если для исключения выбрано необычное условие, время проверки или код ошибки,
объяснение обязательно. Фраза «проверяем условие» таким объяснением не является.

### Где использовать JSDoc

У публичного сервиса, функции, хука или типа с неочевидным контрактом использовать
`/** ... */`. Описывать гарантии, ограничения, побочные эффекты, требования к вызову
и причины отказа. Это должно помогать потребителю без чтения реализации.

- `@param` нужен для смыслового ограничения параметра, а не повторения его типа.
- `@returns` — для гарантии результата, а не фразы «возвращает результат».
- `@throws` — для ожидаемых ошибок и условий возникновения. Не перечислять все
  теоретические исключения платформы и не обещать поведение, которого нет в реализации.
- `@example` — если корректное использование неочевидно.
- Типы в `{...}` не дублировать: TypeScript уже их задаёт.

Пример контракта, связанного с квитанциями операций:

```ts
/**
 * Возвращает сохранённое подтверждение без повторного применения команды.
 * Квитанция проверяется до текущей редакции: последующие изменения дневника
 * не должны мешать повтору команды, ответ на которую был потерян.
 *
 * @param command Неизменяемая команда с тем же идентификатором и содержимым.
 * @throws OperationError Если идентификатор уже использован для другой команды.
 */
async function findPreviousConfirmation(
  command: OperationCommand,
): Promise<OperationConfirmation | null> {
  // Здесь находится поиск квитанции и проверка совпадения содержимого.
  return receiptReader.findMatching(command);
}
```

В этом фрагменте `receiptReader` — условная зависимость; JSDoc описывает контракт,
который её реализация обязана обеспечить.

### Где использовать локальный комментарий

Причину конкретной проверки писать непосредственно перед ней:

```ts
// После восстановления снимка квитанция могла исчезнуть. Старую команду
// отклоняем до её поиска, иначе ранее выполненное изменение применится повторно.
if (command.recoveryGeneration !== currentGeneration) {
  throw new OperationError('RECOVERY_GENERATION_MISMATCH');
}
```

Неудачные комментарии: `// Проверяем поколение`, `// Выбрасываем ошибку`,
`/** Сохраняет черновик. */` над `saveDraft`. Они повторяют код и не объясняют решение.

Комментарии пишутся по-русски и обновляются вместе с поведением. Приводить относительную
ссылку на документ или устойчивое обозначение ADR, если это помогает проверить основание.
Не оставлять историю правок, неподтверждённые предположения и закомментированный старый код.
`TODO` допустим только с конкретным условием завершения и ссылкой на существующую задачу.

## Размер абстракции

Класс оправдан зависимостями, жизненным циклом или управлением состоянием.
Функция подходит для разбора, проверки, расчёта и преобразования данных.
Не заменять чистые функции сервисами только ради единообразия.

Избегать длинных фабрик, возвращающих объект методов над большим изменяемым замыканием.
Объект редактора или сессии должен иметь явный контракт, собственные поля и жизненный цикл.
Не создавать универсальные `Manager`, `Engine`, базовый CRUD и систему плагинов
без конкретной потребности.

## Форматирование

| Параметр | API | Web |
|---|---|---|
| Отступ | 2 пробела | 4 пробела |
| Предпочтительная максимальная ширина | 130 | 120 |
| Кавычки TypeScript | Одинарные | Одинарные |
| Точки с запятой | Да | Да |
| Завершающие запятые в многострочных конструкциях | Да | Да |

Сложные сигнатуры, объекты и JSX переносить раньше предела, если так понятнее.
В JSX использовать двойные кавычки строковых атрибутов. Документация и конфигурация
сохраняют собственный формат. Параметры закреплены в
[конфигурации Prettier](../../.prettierrc.json): `npm run format` форматирует исходники,
контракты, скрипты и тесты, `npm run format:check` проверяет их без изменения.
Сгенерированные файлы и временные каталоги исключены. Линтер архитектурных правил
не подключён: форматтер не проверяет разделение обязанностей и качество комментариев.

## Применение к существующему коду

1. Прочитать контракт, применимые ADR и существующие проверки поведения.
2. Ограничить область конкретным сценарием, классом, компонентом или модулем.
3. Определить сохраняемые гарантии, затем менять структуру.
4. Сохранить сигнатуры и форматы хранения, если задача не требует их изменения.
5. Обновить комментарии: объяснения должны соответствовать новым условиям и порядку действий.
6. Выполнить `npm run typecheck` и применимые проверки поведения. Для правок только
   документации проверять ссылки и согласованность правил.

Не совмещать функциональную задачу с массовым форматированием и перестройкой соседних
модулей. Появление руководства не означает соответствия существующего кода этим правилам.
