# Фронтенд: React

Обязательное руководство для интерфейса, хуков и браузерной логики. Читать вместе
с [общими соглашениями](./coding-conventions.md). Примеры включены в документ
и не требуют других проектов на компьютере.

Примеры списка и формы иллюстрируют организацию кода. Они не означают, что каталог
или API уже реализованы. Общий пример загрузки относится к чтению; запись дневника
проходит через протокол команды, черновика и подтверждения.

## 1. Структура по функции продукта

```text
apps/web/src/
  App.tsx
  diary/
    exercises/
      ExercisesPage.tsx
      exercises.type.ts
      components/
        ExerciseCard.tsx
        ExercisesList.tsx
        PersonalExerciseForm.tsx
      hooks/
        useExercisesList.ts
      api/
        exercises-api.ts
        exercises-contract.ts
      mappers/
        map-exercise-form.ts
    drafts/
      draft-session.ts
      draft-editor.ts
      encrypted-draft-storage.ts
  calculator/
    CalculatorPage.tsx
  components/
    ErrorMessage.tsx
```

Создавать каталоги по необходимости. В маленькой функции компонент, тип и хук могут
лежать рядом без дополнительных папок. Повторно используемый предметный компонент
сначала остаётся в своём контексте. Общий каталог содержит только действительно
общий UI без зависимости от аккаунта, дневника и его API.

Простые страницы состоят из композиции компонентов. Не вводить глобальное дерево
`containers`, отдельную архитектурную методологию, менеджер состояния или универсальный
query-клиент ради сходства со структурой другого проекта.

Калькулятор не импортирует сессию, API и хранилище дневника. Общее оформление
не должно затянуть эти зависимости в его сборку.

## 2. Границы ответственности

| Часть | Обязанность |
|---|---|
| Страница | Собрать экран, связать действия с компонентами, показать состояния |
| Компонент | Отобразить конкретный участок UI и сообщить о действии через props |
| Хук сценария | Согласовать React-состояние, загрузку и действия пользователя |
| API-модуль | Отправить HTTP-запрос, проверить ответ, перевести транспортные ошибки |
| Mapper | Преобразовать форму, DTO или фильтр без побочных эффектов |
| Модуль черновиков | Хранение, шифрование, редакции, неизменяемая команда и подтверждение |

Небольшому локальному `useState` отдельный хук не нужен. Если разметку трудно читать
из-за асинхронного сценария, выносить сценарий в хук. Сам хук не должен становиться
огромным файлом со всеми действиями экрана: загрузка списка, редактирование формы
и управление ключами имеют разные обязанности.

## 3. Компоненты и props

Имена компонентов и файлов — PascalCase. Хуки — `useSomething.ts`, остальные модули —
kebab-case. Компонент объявлять именованной функцией или именованной константой.
Для страницы допустим default export, для вспомогательных компонентов и хуков
предпочтительны именованные экспорты.

```tsx
import type { ReactElement } from 'react';
import { Button, Card } from 'antd';
import type { ExerciseSummary } from '../exercises.type';

type ExerciseCardProps = {
    exercise: ExerciseSummary;
    onSelect: (exerciseId: string) => void;
};

export function ExerciseCard({ exercise, onSelect }: ExerciseCardProps): ReactElement {
    const handleSelect = (): void => {
        onSelect(exercise.id);
    };

    return (
        <Card>
            <h2>{exercise.name}</h2>
            <Button onClick={handleSelect}>Выбрать упражнение</Button>
        </Card>
    );
}
```

Props типизировать рядом с компонентом именованным типом `ExerciseCardProps`.
Передавать необходимые данные, а не весь объект глобальной сессии или сервис.
Для полиморфного компонента сначала проверить, действительно ли нужен generic;
обычные предметные props обычно проще.

Для компонентов допустим явный `ReactElement`, `ReactElement | null`, либо вывод
возвращаемого JSX из именованной функции. `React.FC` допустим, если выбран последовательно,
но `children` всё равно задаётся явно: `children?: ReactNode`. Не добавлять `children`
к компоненту, который их не использует.

Обработчики внутри компонента называть `handleSelect`, `handleSubmit`;
props-события — `onSelect`, `onSubmit`. Маленький callback с одним действием допустим
в JSX, большой асинхронный сценарий выносить из разметки.

## 4. Композиция страницы и состояния

Страница не отправляет HTTP внутри JSX. Она получает данные из хука и выбирает
понятное состояние представления:

```tsx
import { Alert, Empty, Spin } from 'antd';
import { ExercisesList } from './components/ExercisesList';
import { useExercisesList } from './hooks/useExercisesList';

export default function ExercisesPage() {
    const { state } = useExercisesList('');

    if (state.status === 'loading') {
        return <Spin tip="Загружаем упражнения…" />;
    }

    if (state.status === 'failed') {
        return <Alert type="error" message={state.message} showIcon />;
    }

    if (state.items.length === 0) {
        return <Empty description="Упражнений пока нет" />;
    }

    return <ExercisesList exercises={state.items} />;
}
```

Пример не задаёт готовый дизайн экрана. Контракт компонента Ant Design проверяется
по установленной версии при реализации. Для доступного представления загрузки
при необходимости добавить отдельный текст с `role="status"`.

Пустой результат и ошибка — разные состояния. Не показывать «ничего нет» при сетевом
отказе и не заменять все состояния одним boolean. Если при обновлении сохраняется
старый результат, явно моделировать это состояние и показывать, что идёт обновление.

У списков использовать устойчивый `key={exercise.id}`. Индекс допустим только для
действительно неизменяемого списка без собственного состояния строк; не применять его
к подходам и редактируемым упражнениям.

## 5. Хуки с явным контрактом

Хук возвращает данные и именованные действия. Объект обычно понятнее длинного tuple:

```ts
type UseExerciseEditorResult = {
    state: ExerciseEditorState;
    changeName: (name: string) => void;
    submit: () => Promise<void>;
};
```

Публичный результат сложного хука описывать явно. У маленькой обёртки над `useState`
допустим вывод типа. Не использовать публичный результат в виде `ReturnType`
большой внутренней фабрики: это скрывает контракт от читателя.

### Пример загрузки с защитой от устаревшего ответа

`exercisesApi.findMany` ниже — зависимость API-модуля с сигнатурой
`(params: { search: string }, signal: AbortSignal) => Promise<ExerciseSummary[]>`.
Она обязана проверять ответ и учитывать signal.

```ts
import { useEffect, useState } from 'react';
import { exercisesApi } from '../api/exercises-api';
import type { ExerciseSummary } from '../exercises.type';

type ExercisesListState =
    | { status: 'loading' }
    | { status: 'ready'; items: ExerciseSummary[] }
    | { status: 'failed'; message: string };

type UseExercisesListResult = {
    state: ExercisesListState;
};

/**
 * Принимает результат только последнего действующего поиска.
 * Используется внутри границы сессии, которая размонтируется при смене атлета.
 */
export function useExercisesList(search: string): UseExercisesListResult {
    const [state, setState] = useState<ExercisesListState>({ status: 'loading' });

    useEffect(() => {
        const controller = new AbortController();
        let isActive = true;

        const load = async (): Promise<void> => {
            setState({ status: 'loading' });

            try {
                const items = await exercisesApi.findMany({ search }, controller.signal);

                // Отмена запроса не гарантирует отмену уже начавшегося разбора ответа.
                // Проверка защищает новый поиск от результата предыдущего эффекта.
                if (isActive) {
                    setState({ status: 'ready', items });
                }
            } catch (error: unknown) {
                if (!isActive || controller.signal.aborted) {
                    return;
                }

                setState({ status: 'failed', message: 'Не удалось загрузить упражнения' });
            }
        };

        void load();

        return () => {
            isActive = false;
            controller.abort();
        };
    }, [search]);

    return { state };
}
```

`void load()` допустим здесь потому, что ожидаемый отказ обрабатывается внутри `load`.
Оператор `void` сам по себе не обрабатывает rejected promise.

При смене атлета нужно немедленно скрыть данные и сбросить сессионное состояние,
а не ждать нового `useEffect`. Например, граница дневника может размонтировать
дерево по устойчивому идентификатору сессии; очищение ключей и открытых черновиков
при этом выполняется отдельно. `key` не является механизмом авторизации.

## 6. Эффекты, refs и мемоизация

- `useEffect` синхронизирует компонент с внешней системой: запросом, подпиской,
  браузерным событием. Не использовать эффект для вычисления значения, которое
  получается из props или состояния обычным выражением.
- У эффекта есть полный список зависимостей и cleanup для созданных ресурсов.
  Не отключать правило зависимостей ради подавления повторного запуска.
- Не делать callback эффекта `async`; асинхронную функцию объявлять внутри.
- Не запускать запись дневника из эффекта монтирования: повторный запуск компонента
  не должен создавать предметную операцию. Отправка остаётся явным действием атлета.
- Обновление, зависящее от предыдущего значения, использовать в функциональной форме:
  `setCount((count) => count + 1)`.
- `useRef` подходит для императивного ресурса, номера запроса или блокировки; данные,
  влияющие на отображение, должны уведомлять React через state или подписку.
- `useMemo` и `useCallback` применять при конкретной потребности в стабильной ссылке
  или дорогом вычислении. Не добавлять их к каждому callback «для оптимизации».
- Не создавать универсальный `useApi` с десятками опций, пока нет ясного повторяющегося
  контракта. Простые предметные хуки предпочтительнее скрытого поведения.

## 7. Формы: представление отдельно от сценария

Форма описывает поля, локальную валидацию и события. Создание, редактирование,
отправка команды и восстановление черновика — ответственность внешнего сценария.
Одна форма может использоваться в нескольких сценариях с разными обработчиками.

```tsx
import type { ReactElement } from 'react';
import { Alert, Button, Form, Input } from 'antd';

export type PersonalExerciseFormValues = {
    name: string;
};

type PersonalExerciseFormProps = {
    initialValues: PersonalExerciseFormValues;
    isSubmitting: boolean;
    errorMessage?: string;
    onSubmit: (values: PersonalExerciseFormValues) => Promise<void>;
    onCancel: () => void;
};

/**
 * Не очищает поля после отправки: момент подтверждения определяет сценарий записи.
 * onSubmit обязан обработать отказ и передать его через errorMessage.
 */
export function PersonalExerciseForm({
    initialValues,
    isSubmitting,
    errorMessage,
    onSubmit,
    onCancel,
}: PersonalExerciseFormProps): ReactElement {
    const handleFinish = (values: PersonalExerciseFormValues): void => {
        void onSubmit(values);
    };

    return (
        <Form<PersonalExerciseFormValues>
            layout="vertical"
            initialValues={initialValues}
            onFinish={handleFinish}
        >
            <Form.Item
                name="name"
                label="Название упражнения"
                rules={[{ required: true, whitespace: true, message: 'Введите название' }]}
            >
                <Input />
            </Form.Item>

            {errorMessage && <Alert type="error" message={errorMessage} showIcon />}

            <div className="flex flex-wrap gap-2">
                <Button type="primary" htmlType="submit" loading={isSubmitting}>
                    Сохранить
                </Button>
                <Button htmlType="button" onClick={onCancel} disabled={isSubmitting}>
                    Отмена
                </Button>
            </div>
        </Form>
    );
}
```

Это представление формы, а не реализация сохранности ввода. Для реального редактора
изменения полей подключаются к модулю черновиков. Контракт `onSubmit` в примере требует
обработки отказа: нельзя передать произвольную rejected promise и надеяться, что `void`
её обработает. При необходимости выбрать другой контракт результата и обработать его явно.

`initialValues` — начальное значение, а не механизм синхронизации со сменой записи.
Переход к другому упражнению моделировать явно; не вызывать `setFieldsValue` на каждый
новый объект props, стирая текущий ввод. Не дублировать все значения формы в `useState`
без конкретной необходимости. Состояние черновика имеет отдельную ответственность.

Преобразование формы в параметры команды оформлять чистой функцией:

```ts
type RenamePersonalExercisePayload = {
    exerciseId: string;
    name: string;
};

export function mapFormToRenamePayload(
    exerciseId: string,
    values: PersonalExerciseFormValues,
): RenamePersonalExercisePayload {
    return {
        exerciseId,
        name: values.name.trim(),
    };
}
```

Это payload, а не полная команда: ID операции, владелец, поколение восстановления
и редакция добавляются протоколом. Нормализация должна совпадать с серверным контрактом;
она не заменяет серверную проверку. Веса сохраняют согласованный десятичный формат.

## 8. API-модули и контракты

API-модуль скрывает URL, HTTP-статусы и разбор данных. Потребитель получает типизированный
результат или распознаваемую ошибку. Ответ `response.json()` рассматривать как `unknown`:

```ts
async function readExercisesResponse(response: Response): Promise<ExerciseSummary[]> {
    if (!response.ok) {
        throw await parseApiError(response);
    }

    const body: unknown = await response.json();

    return parseExercisesResponse(body);
}
```

`parseApiError` и `parseExercisesResponse` — явные парсеры runtime-данных.
Нельзя заменить их `as ExerciseSummary[]`. Сгенерированный клиент допустим, если он
реально подключён к принятому контракту; не копировать генератор и настройки автоматически.

- Не импортировать серверную реализацию, Prisma и секреты в браузер.
- Общие транспортные типы при необходимости выделяются в нейтральный модуль контракта;
  перестройка существующего импорта требует отдельного осмысленного изменения.
- Фильтры передавать объектом с именованными полями. Не писать вызовы с длинной цепочкой
  позиционных `undefined`; такой клиент оборачивать небольшим предметным адаптером.
- Не показывать пользователю сырой `error.message` от неизвестного исключения.
  Известные коды переводить в подходящий текст, неизвестные — в безопасное сообщение.
- Не сводить чтение с ошибкой к пустому массиву. Транспортный отказ должен оставаться
  отличимым от успешного отсутствия данных.
- Разбирать URL-фильтры явными парсерами, а не приводить строку к union через `as`.
  Календарную дату не превращать автоматически в UTC-момент.

## 9. Черновики и подтверждение записи

Браузерная логика хранения не должна быть спрятана в JSX или огромном хуке.
Разделять обязанности: encrypted storage работает с записями IndexedDB,
session управляет доступом и ключом, editor — состоянием ввода и подготовленной командой.
Конкретное деление уточняется задачей; не создавать классы ради одного короткого метода.

У сложного редактора должны быть явные состояние, переходы и жизненный цикл.
Возможная форма контракта:

```ts
interface DraftEditor {
    snapshot(): EditorSnapshot;
    edit(fields: EditorFields): Promise<void>;
    prepareCommand(): Promise<PreparedCommand>;
    sendPreparedCommand(): Promise<void>;
    dispose(): void;
}
```

Это иллюстрация интерфейса; конкретные типы задаются протоколом. Если внешний объект
изменяет состояние асинхронно, у React должна быть подписка или другой явный механизм
обновления. Одного вызова `snapshot()` при монтировании недостаточно.
Класс редактора может получать хранилище и транспорт через конструктор. В callback
не держать несколько неявных версий владельца, ключа и состояния.

При рефакторинге сохранять гарантии [ADR-0021](./adr/ADR-0021-durable-drafts-and-operation-receipts.md):

- шифрование и разделение владельцев, ключ в памяти, ciphertext в IndexedDB;
- отсутствие ложного сообщения о сохранении до завершения транзакции IndexedDB;
- явное состояние отказа локального хранения;
- неизменяемую подготовленную команду и её UUID при повторе;
- различие «сервер отказал» и «ответ неизвестен» после потери связи;
- очистку только подтверждённой редакции, без удаления более свежего ввода;
- скрытие открытых данных и очистку ключа при выходе или потере доступа;
- запрет подменять поколение восстановления внутри старой команды.

Причины этих проверок описывать JSDoc и локальными комментариями. Например:

```ts
// Ответ относится к прежней редакции. Атлет мог продолжить ввод во время запроса,
// поэтому подтверждение не даёт права удалить более свежий черновик.
await draftStorage.removeIfRevisionMatches(
    confirmation.draftId,
    confirmation.localRevision,
);
```

Поля и метод здесь условные. `removeIfRevisionMatches` должен сравнивать редакцию
и удалять запись в одной транзакции хранилища. Отдельная проверка в памяти перед
безусловным удалением оставляет гонку и этому контракту не соответствует.

## 10. Оформление и доступность

Использовать Ant Design для элементов управления и Tailwind для компоновки.
Тему менять токенами, а не набором хрупких переопределений внутренних CSS-классов.
Собственный компонент над Ant Design нужен для повторяемого поведения или
предметного представления, а не для переименования каждой кнопки.

Ориентир — мобильный браузер: карточки, компактные формы, доступные действия,
без обязательной широкой таблицы. Поля имеют label, кнопки понятные названия,
ошибки доступны для вспомогательных технологий. Не использовать кликабельный `div`
вместо кнопки и один цвет как единственный способ показать состояние.

Загрузка, успех и ошибка должны сообщаться последовательно. Важный отказ сохранения
не должен существовать только в кратком toast. После асинхронного действия не терять
фокус и введённые значения без причины.

## 11. Комментарии и проверки

JSDoc обязателен для неочевидных контрактов хука, формы и редактора: кто обрабатывает
ошибку, когда можно очистить данные, как отменяется работа, что считается подтверждением.
Локальный комментарий объясняет защиту от устаревшего ответа, особый переход состояния
или исключение. Не подписывать очевидное `setIsOpen(true)` фразой «открываем окно».

Проверять поведение, которое может сломаться при изменении структуры:

- ошибка загрузки отличается от пустого списка;
- устаревший ответ не заменяет результат нового поиска;
- отменённый эффект не показывает ложную ошибку;
- ввод сохраняется после отказа сервера;
- повтор отправляет прежнюю команду;
- подтверждение старой редакции не очищает новый ввод;
- смена аккаунта немедленно скрывает данные предыдущего;
- основные действия доступны с клавиатуры и на мобильном экране.

Проверки IndexedDB и жизненного цикла выполняются в подходящей браузерной среде.
Mock функции хранения не доказывает завершение транзакции или очистку ключей.
Не добавлять тест, который только повторяет JSX без проверки полезного поведения.
Выполнять проверку типов и применимые существующие тесты после изменений кода.
