# Пользователь один — Атлет; тренер появится позже как право доступа, а не роль

**Статус:** Принят; совместный доступ — не в первой версии, см. [backlog.md](../../backlog.md), «Совместный доступ (тренер)»  
**Дата:** 2026-09-06  

В системе один тип пользователя: **Атлет**. Он сам ведёт свой дневник и сам строит себе
тренировки — цикл, неделю, веса. В первой версии никто, кроме него, к дневнику доступа не имеет.

Когда совместный доступ появится, «тренер» будет не ролью, а атлетом, которому владелец дневника
выдал право править свой план. Отдельной роли, отдельного интерфейса и разделения маршрутов
по ролям не будет. Инвариант уже сейчас: **факт выполнения правит только владелец дневника**.

## Считанные альтернативы

- **Две роли — тренер и атлет**, роль задаётся при аутентификации, у каждой свой раздел.
  Отвергнуто: ломает главный сценарий продукта — «друг зарегистрировался и ведёт себя сам»;
  такому пользователю неоткуда взять тренера, а атлет без тренера не может составить план
  сам себе.
- **Совместный доступ в первой версии.** Отвергнуто: пока в продукте нет ядра — цикла, истории,
  накопленных данных, — второму человеку в дневнике нечего делать.
- **Заложить разделение владельца и автора изменения в модель заранее.** Отвергнуто вместе
  с отсрочкой совместного доступа: в модель первой версии не закладывается функциональность,
  отложенная без даты.

## Последствия

- В первой версии правило доступа одно: атлет видит и правит только свой дневник
  ([auth](../../requirements/auth/index.md), R1).
- Ролей в системе нет, права определяются владением.
- При возврате к совместному доступу разделение владельца и автора изменения придётся добавить
  к уже накопленным данным — сознательная плата за отсрочку. Решения, принятые до отсрочки,
  собраны в [backlog.md](../../backlog.md).
