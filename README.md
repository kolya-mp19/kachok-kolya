# Kachok Kolya

**Главная задача приложения — удобное ведение дневника тренировок и составление плана
на будущие тренировки.** Атлет быстро записывает план, отмечает выполненное, обращается
к истории и на её основе планирует дальше.

Дневник предназначен для регулярно тренирующихся атлетов, прежде всего пауэрлифтеров.
Быстрый ввод, копирование структуры тренировок и запись факта по подходам служат этой
основной задаче. Цикл организует план во времени.

Подсказки и расчёт весов — вспомогательная возможность при составлении плана.
Первая проходка в итогах завершённого цикла устанавливает исходный МПВ; от него приложение
предлагает веса следующих циклов и цель проходки. МПВ повышается только по подтверждённому
результату в итогах следующего завершённого цикла. Отсутствие МПВ и расчётных подсказок
не мешает составлять план внутри цикла и вести дневник с первой тренировки.

Калькулятор работает отдельно от дневника: сравнивает результаты в строгом подъёме
на бицепс по собственному весу и лучшей попытке спортсмена.

В репозитории есть документация, локальная основа E004 и основа хранения E005:
React SPA, NestJS, PostgreSQL и Prisma Migrate. Локальные E004/E005 разрешены до
завершения E003; аутентификация, внешние интеграции, удалённая инфраструктура и выпуск
не реализованы. Блокеры внешних доступов E003/S01 сохраняются.

## Локальный запуск

Нужны Node.js 24.19.x (или более новый 24.x) и npm 11.x. Команды выполняются из корня
репозитория в PowerShell или обычном терминале; Docker, БД, домен и рабочие секреты не нужны.

```powershell
Copy-Item .env.example .env
npm ci
npm run dev
```

Откройте <http://127.0.0.1:5173>. API доступен через `/api/health`; Vite передаёт
`/api` в NestJS на `127.0.0.1:3000`. Остановка обоих процессов — Ctrl+C.
В `.env` нет обязательных значений; необязательный `PORT` меняет порт API.
Порт интерфейса 5173 фиксирован, занятый порт приводит к ошибке запуска.
Оба сервера слушают только loopback. Для проверки используйте мобильный режим браузера;
публичный HTTPS и доступ с телефона настраиваются отдельно после внешних входов E003.

```powershell
npm run build
npx playwright install chromium
$env:TEST_DATABASE_URL='postgresql://kachok:local-only-password@127.0.0.1:54329/kachok_local'
npm test
npm start
```

Собранная оболочка доступна на <http://127.0.0.1:3000> (или порту из `.env`).
NestJS обслуживает статику и известные точки входа SPA; неизвестный API возвращает JSON 404.
`npm run typecheck` отдельно проверяет сервер, клиент и конфигурацию Vite.
Перед полным `npm test` подготовьте локальную PostgreSQL по разделу ниже. Проверки
хранения требуют `TEST_DATABASE_URL` и не пропускаются при его отсутствии.
HTTP-проверка запускает собранный сервер на порту 3017; этот порт должен быть свободен.
Браузерная проверка использует свободный порт 3018 и Chromium Playwright: прямые входы,
мобильную компоновку, задержку и сбой загрузки модулей, обновление и переход при ошибке.
Для установленного Chromium можно задать полный путь к исполняемому файлу через
`PLAYWRIGHT_CHROMIUM_EXECUTABLE_PATH`; обычно используется браузер из команды установки выше.
Отдельный прогон: `node --test tests/mobile-shell.test.mjs` после сборки.
Проверка начинается после сборки. `npm run dev:web` запускает независимый клиент без API.
Для воспроизведения в чистом каталоге клонируйте репозиторий и выполните эти команды;
не копируйте `node_modules`, `dist` и `.env` с другой машины.

Серверные секреты не попадают в Vite: клиент не использует параметры окружения.
Префикс `VITE_` предназначен только для публичных данных. Реальные секреты не добавляются
в исходники, `.env.example` и клиентскую сборку; локальный `.env` исключён из git.

Структура: [клиент](apps/web/src/main.tsx), [сервер](apps/api/src/main.ts),
[сценарий проверки](tests/local-launch.test.mjs). Формулы и дневник появятся в следующих эпиках.

## Локальное хранилище

Нужен запущенный Docker Desktop/Engine с Compose. Используются [PostgreSQL 18.6](https://www.postgresql.org/support/versioning/),
Prisma ORM/Migrate и PostgreSQL-адаптер 7.10.1, драйвер pg 8.16.3. Prisma 7 остаётся
[поддерживаемой веткой](https://www.prisma.io/docs/orm/v7); её
[адаптер и конфигурация](https://www.prisma.io/docs/guides/upgrade-prisma-orm/v7)
совместимы с Node 24. `npm run build` сам генерирует Prisma Client; результат
генерации находится в `node_modules` и не сохраняется в git.

```powershell
docker compose up -d --wait postgres
npm run db:generate
npm run db:migrate
npm run db:status
npm run db:check
```

Команды используют серверный `DATABASE_URL` из `.env`; образец относится только
к синтетическим локальным данным. Поддерживается стандартная схема public; иной ?schema отклоняется до подключения и изменения БД. PostgreSQL доступна на loopback-порту 54329,
данные живут в постоянном томе. `docker compose stop` и повторный `up` сохраняют
данные; удаление тома не является способом исправления миграции.
Оболочка, `/api/health` и калькулятор от БД не зависят. Подключение будущих серверных
модулей — через `createStorage`/`checkStorage` в
[границе хранения](apps/api/src/storage/storage.ts), с обязательным `$disconnect`
при остановке. Эта проверка соединения не является проверкой сессии или владельца.

Готовые SQL-миграции находятся в [каталоге Prisma](prisma/migrations).
Начальная миграция фиксирует техническую версию без продуктовых таблиц. Новая
модель добавляется своим эпиком: подготовить SQL через `prisma migrate dev` на
отдельной синтетической БД, просмотреть SQL и проверить обновление прежней схемы.
Для атомарных PostgreSQL-изменений SQL явно содержит `BEGIN`/`COMMIT`: Prisma Migrate
не добавляет их автоматически. Применённые миграции не переписываются.
В приложение передаются точные десятичные строки; продуктовых полей веса здесь нет.

`db:status` возвращает подтверждённые идентификаторы миграций и завершается
неуспехом при незавершённой истории. CLI скрывает сырой вывод ORM: различаются
`STORAGE_CONFIG_INVALID`, `STORAGE_UNAVAILABLE` и `MIGRATION_FAILED` с этапом и допустимым идентификатором неуспешной миграции (если он доступен в истории),
без URL, SQL и исходного текста исключения. Локальная PostgreSQL также подавляет
исходные SQL-ошибки, способные содержать личные значения; проверка доступности
и контроль миграций выполняются командами выше.

После неуспеха остановите обновление. Сначала проверьте доступность БД через
`db:check`, затем историю через `db:status`. Проверьте SQL готовой миграции в
исходниках и воспроизведите её на отдельной синтетической БД. Не включайте
SQL/параметры в журналы и не публикуйте содержимое `_prisma_migrations.logs`.
Если SQL был частично применён, сначала установите фактическое состояние и
подготовьте проверенное исправление. `prisma migrate resolve --rolled-back <имя>`
допустим только после подтверждённого отката; `--applied` — после завершения
всех предусмотренных изменений. Эти команды меняют историю, а не откатывают SQL.
Не используйте reset, очистку БД или тома. Возврат версии и полное восстановление
регулирует [проект E003](docs/implementation/epics/e003-release-design/design/release-and-recovery.md);
операционная приёмка восстановления остаётся E029.

Полный набор тестов требует собранного приложения, Chromium и БД из Compose:

```powershell
docker compose up -d --wait postgres
npm run build
$env:TEST_DATABASE_URL='postgresql://kachok:local-only-password@127.0.0.1:54329/kachok_local'
npm test
```

Это административное подключение **только к синтетическому локальному кластеру**:
тесты создают случайные отдельные БД `e005_*` и удаляют только их в `finally`,
не изменяя схему `kachok_local`. Проверка журналов использует локальный Compose.
Целевой прогон — `node --test tests/storage.test.mjs`. Проверяются чистая схема,
повтор и новый процесс, обновление прежней проверочной схемы с сохранением строки,
неуспех миграции и отсутствие контрольного секрета в CLI и журнале PostgreSQL.
Постоянных проверочных таблиц в приложении нет.

## Граница личной операции

Серверный модуль подключает [createOwnedOperations](apps/api/src/access/owned-operation.ts)
в месте сборки зависимостей приложения. Его `verifyAccess` — серверный адаптер
актуальной сессии и необходимой защиты операции (CSRF/Origin для изменения),
реализуемый в S04. Адаптер не берётся из тела/заголовков запроса, не доверяет
переданному `athleteId` и при каждом вызове возвращает подтверждённого владельца
либо отсутствие доступа. Постоянные сессии и HTTP-маршруты входа здесь не созданы.

`run(credential, expectedAthleteId, operation)` проверяет доступ заново, затем
сверяет ожидаемого владельца команды. Только после совпадения `operation` получает
неизменяемый контекст `{ athleteId }` из серверного результата. Отсутствие доступа
даёт `ACCESS_REQUIRED`, несовпадение — `OWNER_MISMATCH`, без личных идентификаторов
в сообщении. Проверка не кешируется между операциями.

Прикладной обработчик использует этот `athleteId` во всех запросах и проверяет
принадлежность корневых и вложенных личных ссылок. Чужой и отсутствующий объект
должны давать одинаковое «Не найдено». Граница не заменяет эти проверки.
Для команды с транзакцией после получения общей блокировки владельца необходимо
повторно вызвать ту же границу с теми же доказательствами доступа до чтения квитанции
и изменения данных: отзыв сессии не должен пропускать ожидавшую команду.
Транзакции и квитанции подключаются в T003; реальные сессии — в S04.

Технический проход `node --test tests/owned-operation.test.mjs` после сборки
проверяет передачу владельца, отказ недоверенному JSON и чужому владельцу,
неизменяемость контекста и новый отказ после отзыва синтетического доступа.
Это проверка механизма, а не готовность аутентификации или изоляции двух реальных
аккаунтов. Калькулятор этот модуль не импортирует и API доступа не вызывает.

## Подключение сохранности ввода

Техническая основа E005 не добавляет формы, аутентификацию или маршруты записи.
Сервер подключает [хранилище операций](apps/api/src/operations/operation-store.ts)
через `createOperationStore(storage, ownedOperations, recoveryGeneration)`.
Это автономная точка сборки: выполнение находится в
[OperationsService](apps/api/src/operations/operations.service.ts), запросы — в
[репозитории квитанций](apps/api/src/operations/operation-receipts.repository.ts) и
[репозитории ключей](apps/api/src/operations/draft-keys.repository.ts).
В NestJS тот же граф зависимостей подключается через
[OperationsModule.register](apps/api/src/operations/operations.module.ts) с
`databaseUrl`, `recoveryGeneration` и серверным `verifyAccess`.
Модуль экспортирует `OperationsService` и закрывает клиент БД при остановке приложения.
Автономный вызывающий код закрывает переданный клиент самостоятельно.
До реализации сессий модуль не подключён к `AppModule` и не публикует HTTP-маршруты.
Поколение — обязательная стабильная случайная строка серверной конфигурации **вне
БД**. Её создают один раз, например `node -p "require('node:crypto').randomUUID()"`,
сохраняют вместе с серверной конфигурацией и меняют до открытия восстановленной
БД. На обычном запуске новое поколение не генерируется. Калькулятор его не получает.

`getDraftKey` проверяет владельца через границу T002 и возвращает его ключ AES-256-GCM.
При продолжении черновика обязательно передать его прежний `keyId`: отсутствующий
ключ даёт `DRAFT_KEY_MISSING`, а не создаётся под прежним идентификатором. Реальный
маршрут выдачи ключа создаётся в S04: только подтверждённая сессия, HTTPS и
`Cache-Control: no-store`, без произвольного выбора владельца.

`execute(credential, envelope, handler)` принимает версию протокола, UUID операции,
ожидаемого владельца, поколение, вид команды, корень, базовую редакцию, фактическую
дату и JSON payload. Дополнительные поля отвергаются; payload — конечные JSON
значения, без `undefined`, `NaN`, классов, циклов и секретов доступа. Сервер фиксирует
неизменяемый snapshot и вычисляет SHA-256 канонического JSON с сортировкой ключей.
Десятичные веса передаются строками. Клиентский хеш не используется как доказательство.

В транзакции Serializable берётся PostgreSQL advisory lock владельца
`hashtextextended(athleteId, 0)`, затем повторяется актуальная проверка доступа T002.
Будущие календарь, пересчёт и отзыв доступа используют тот же порядок блокировки.
Поколение проверяется до квитанции, квитанция — до редакции. Совпавший UUID с другим
хешем даёт конфликт; повтор возвращает исторический результат. `findReceipt` доступен
только подтверждённому владельцу с актуальным поколением. Квитанции не имеют TTL.

`handler.currentRevision(tx, owner, command)` приводит календарь и читает редакцию
своего прикладного корня; `handler.apply(tx, owner, command)` проверяет доменные
условия и возвращает `{ revision, result }`. Все источники, фиксация и пересчёт
меняются через переданный `tx`, в одной транзакции с квитанцией. В обработчике нет
внешних вызовов: сериализационный отказ повторяет **всю** транзакцию не более трёх
попыток. После исчерпания или неизвестного отказа возвращается `OPERATION_FAILED`
без SQL/параметров; этот исход не доказывает клиенту отсутствие записи. Ожидаемый
окончательный доменный отказ можно выразить `OperationError('OPERATION_REJECTED')`.

В браузере [openPendingInput](apps/web/src/diary/pending-input.ts) получает ключ,
его идентификатор, подтверждённого владельца и поколение только из серверного
адаптера S04. Ключ импортируется как неэкспортируемый CryptoKey и остаётся в памяти.
Состояние и жизненный цикл разделены между
[сессией](apps/web/src/diary/drafts/pending-input-session.ts),
[редактором](apps/web/src/diary/drafts/draft-editor.ts),
[шифрованием](apps/web/src/diary/drafts/encrypted-draft-storage.ts) и
[репозиторием IndexedDB](apps/web/src/diary/drafts/indexed-draft.repository.ts).
Расшифрованные данные проверяются парсером состояния; существующий формат записей сохраняется.
`openEditor(draftId, baseRevision)` продолжает независимый редактор; `edit(fields)`
сразу меняет поля в памяти и последовательно сохраняет ciphertext в IndexedDB.
Каждая запись использует новый 96-битный IV; AAD связывает формат, владельца, ключ,
черновик и редакцию. CAS и `transaction.complete` защищают от устаревшей записи.
`snapshot()` возвращает поля и техническое состояние для будущей формы: `saving`
до завершения локальной транзакции, затем `draft`/`ready`. Блокировка и повторный вход
сериализованы: повторный `lock` и `resume` ожидают завершения прежней записи/очистки.

`prepare({commandType, rootId, payload, occurredOn})` сохраняет неизменяемый envelope.
`send(transport)` начинает сеть только после завершённой локальной транзакции.
`retry(transport)` вручную повторяет тот же envelope; фоновой очереди нет. Адаптер
transport использует текущую сессию/CSRF и преобразует отказ авторизации в
`ACCESS_REQUIRED`, окончательные отказы — в соответствующие коды протокола.
Неизвестный исход сохраняет ввод и pending-команду; поздний ответ удаляет только
отправленную редакцию. Более новая правка сохраняет прежнюю базовую редакцию.
`observeConfirmed({revision, result})` передаёт заведомо актуальное серверное чтение;
историческая квитанция остаётся отдельно в `lastReceipt` и не подменяет это чтение.
После окончательного отказа `reconcile(baseRevision)` вызывается только по явной
сверке атлетом; затем `prepare` создаёт новый UUID. Неопределённую отправку так
заменить нельзя. Старое поколение внутри прежней команды не переписывается.

При выходе/истечении/смене аккаунта вызывается `session.lock()`: отправки прекращаются,
другие вкладки получают BroadcastChannel-сигнал без секретов, поля и ключ удаляются
из активного состояния, поздние ответы игнорируются. После нового сетевого входа
того же владельца `resume(material)` позволяет открыть редактор заново; прежние
editor handles остаются недействительными. Перед показом после возврата из фона
интеграция S04 сначала блокирует редактор и перепроверяет сессию. `close()` освобождает
соединения и канал без оповещения о выходе других вкладок.

При квоте/недоступной IndexedDB поля имеют состояние `memory`, отправка не начинается;
`retryLocal()` повторяет локальную запись. Если затем требуется блокировка, последний
успешно зашифрованный ввод остаётся только как volatile ciphertext в этой вкладке и
может быть прочитан после `resume` прежним ключом. Закрытие вкладки в таком состоянии
теряет его; ошибка шифрования также не даёт обещания сохранности. Ошибка расшифровки
не удаляет ciphertext. Запрашивается persistent storage, но `persistentStorage=false`
не выдаётся за гарантию. Даже успешная IndexedDB не защищает от очистки сайта,
вытеснения или отказа устройства.

Целевые проверки после сборки: `node --test tests/pending-operation.test.mjs` с
тестовой PostgreSQL и `node --test tests/pending-input.test.mjs` с Chromium.
Браузерная проверка использует Vite на свободном loopback-порту 3020 и настоящие
IndexedDB/WebCrypto без временного продуктового интерфейса. S04 принимает реальные
сессии и аккаунты; S06–S07 — формы и настоящую запись плана/факта; E029 — восстановление
полного снимка. E003/S01 и внешние доступы остаются незавершёнными.
